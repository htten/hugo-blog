## 引言：你可能早就遇到过这些问题

- 补全建议明明很准，可一旦涉及跨文件的重构，模型就像"没看见"其它文件里的定义。
- 同一个 Agent，换个代码库就明显变笨：不是模型变差了，而是它"没找到"相关代码。
- 索引一个 5 万文件的仓库要等好几分钟，用户第一次提问时什么都搜不到。
- 补全的延迟要求是 100 毫秒量级，Agent 一轮要几十秒，两者的工程约束完全不同，却经常被当成同一个系统来设计。
- 代码库里的密钥、内部实现、未发布的需求，全都被索引进了某个向量库。

这些问题的共同根源是：**AI 编程助手不是一块"会写代码的模型"，而是一条生产链路**——补全负责毫秒级的即时响应，Agent 负责多步的自主执行，代码库检索负责让模型"看见"仓库，沙箱负责安全地执行。任何一段的设计选择都会同时影响延迟、成本、精度和安全。

本文按这条链路展开，并在最后给出一份可以照着做的落地清单。

## 一、补全：代码补全的模型原理

### 1.1 为什么是 FIM 而不是纯左到右生成

自然语言模型是左到右的：给它前文，它预测下一个 token。但代码不是这样写的。

程序员写代码时，光标前面有内容，光标后面也有内容。很多时候你是在两个已有代码块**之间**插入一段逻辑——比如补全一个 `if` 分支的中间部分、填充一个函数的实现、在两个已实现的辅助函数之间写调用代码。纯左到右模型对这种场景是无能为力的，因为它看不到光标后面的内容。

**FIM（Fill-In-the-Middle，中间填充）** 就是为了解决这个问题：训练时把一段代码拆成前缀（prefix）、中间（middle）、后缀（suffix）三部分，让模型学习**给定前后文、预测中间缺失的部分**。推理时，光标前的代码作为前缀，光标后的代码作为后缀，模型生成中间该填的内容。

DeepSeek-Coder 在训练中明确采用了 fill-in-the-blank 任务配合 16K 窗口来增强代码生成与 infilling 能力（[arXiv:2401.14196](https://arxiv.org/abs/2401.14196)）。Code Llama 则在 7B、13B、70B 三个尺寸上支持"基于上下文内容"的 infilling（[arXiv:2308.12950](https://arxiv.org/abs/2308.12950)）。

这个机制的工程含义很直接：**补全请求不是"续写"，而是"填空"**。它决定了你在构造请求时，光标位置是一个一等公民，而不只是文本里的一个偏移量。

### 1.2 上下文从哪来

补全的质量上限，很大程度上不取决于模型，而取决于**你给了它什么上下文**。典型的上下文来源按"离光标的距离"由近到远排列：

| 层级 | 内容 | 典型 token 量 | 价值 |
| --- | --- | --- | --- |
| 光标所在行/块 | 正在编辑的代码 | 几十到几百 | 最高 |
| 光标前后文（FIM） | 前后各若干行 | 几百到几千 | 很高 |
| 当前文件 | 整个文件 | 几百到几千 | 高 |
| 相关打开文件 | 其它标签页 | 视情况 | 中 |
| imports / 依赖声明 | 引用了哪些库 | 几百 | 中 |
| 同目录 / 同项目文件 | 邻近模块 | 几千 | 中 |
| 项目级检索结果 | 相关函数、类型定义 | 视预算 | 中高 |

关键矛盾在于：**信息越多越好，但 token 预算是有限的**。补全请求对延迟极其敏感，上下文越长，prefill 越慢，建议越可能"过期"（用户已经开始打字，建议才到达）。

所以工程上要做的是**按 token 预算做分层裁剪**，而不是把所有能拿到的上下文都塞进去。这也是为什么补全系统通常需要一个独立的"上下文组装器"组件，而不是把整个文件原样传给模型。

### 1.3 延迟预算：100 毫秒是一道硬门槛

补全场景有一个非常明确的延迟约束：**建议必须在用户继续打字之前到达**。

Pythia 论文（部署在 VS Code 里的 IntelliCode）给出的设计目标是 **100 毫秒量级**返回排序后的方法/API 推荐（[arXiv:1912.00742](https://arxiv.org/abs/1912.00742)）。这个量级不是随意定的：人打一个词的速度通常在几百毫秒，一旦建议延迟超过这个尺度，用户已经输入了下一个词，建议要么显得多余，要么会"抢"光标导致体验崩坏。

100 毫秒的预算对模型规模有直接约束：

- **模型不能太大**：1.3B~15B 是补全的常见区间，再大 prefill 就压不进预算；
- **上下文不能太长**：prefill 时间与输入长度近似线性，上下文翻倍延迟就翻倍；
- **量化与投机解码是常规手段**：在可接受的精度损失内换取延迟。

这也是补全和 Agent 最根本的架构分歧：**补全追求"快而够用"，Agent 追求"慢而做对"**。把两者混为一谈，是很多编程助手项目早期踩的坑。

### 1.4 模型选型

近年开源代码模型的进展很快，几个有代表性的系列：

| 模型 | 尺寸 | 训练规模 | 特点 |
| --- | --- | --- | --- |
| DeepSeek-Coder | 1.3B~33B | 2 万亿 token（从零） | fill-in-the-blank + 16K 窗口；许可证宽松 |
| StarCoder2 | 3B / 7B / 15B | 3.3~4.3 万亿 token | The Stack v2 覆盖 619 种语言；OpenRAIL |
| Qwen2.5-Coder | 0.5B / 1.5B / 3B / 7B / 14B / 32B | 5.5 万亿+ token | 基于 Qwen2.5 继续预训练；10+ 基准 SOTA |
| Code Llama | 7B / 13B / 34B / 70B | 16k 序列，支持 100k 输入 | 7B/13B/70B 支持 infilling |

数据来源：DeepSeek-Coder（[arXiv:2401.14196](https://arxiv.org/abs/2401.14196)）、StarCoder2（[arXiv:2402.19173](https://arxiv.org/abs/2402.19173)）、Qwen2.5-Coder（[arXiv:2409.12186](https://arxiv.org/abs/2409.12186)）、Code Llama（[arXiv:2308.12950](https://arxiv.org/abs/2308.12950)）。

几个值得注意的事实：

- **小模型可以打过大模型**：StarCoder2-3B 超过了 StarCoderBase-15B，15B 匹配或超过 CodeLlama-34B。这不是"模型变大"的故事，而是"训练数据更干净、更多样"的故事。
- **训练语料的覆盖面决定上限**：StarCoder2 背后的 The Stack v2 覆盖 619 种编程语言。如果你的业务是某种小众语言，通用模型的表现会明显打折。
- **许可证是工程约束**：DeepSeek-Coder 与 Code Llama 都允许商业使用，但具体条款不同。选型时必须过法务，不能只看 benchmark。

### 1.5 评测：top-k 准确率与接受率是两回事

补全有两个不同层次的指标，混用它们会导致错误的优化方向：

- **top-k 准确率**：模型给出的前 k 个候选中是否包含"正确"的代码。Pythia 在 2700 个 Python 开源仓库上报告 top-5 准确率 92%，比基线平均高 20%。这是一个**离线指标**，衡量模型的排序能力。
- **接受率**：用户实际采纳了多少条建议。这是一个**在线产品指标**，受延迟、UI 呈现方式、上下文质量、用户习惯等大量非模型因素影响。

两者的差距可能非常大：一个 top-5 准确率 92% 的模型，在线接受率可能只有 20%~30%，因为用户会忽略不符合当前意图的建议。

**工程结论**：不要只看离线 benchmark 选模型，要在自己的真实代码库上做 A/B 测试。离线指标是必要条件，不是充分条件。

## 二、Agent：从补全到自主编码

### 2.1 Agent 循环

补全是"一次预测"，Agent 是"一个闭环"：

```
理解任务 → 定位相关代码 → 修改 → 运行/测试 → 观察结果 → 修正 → 再运行 → 交付
```

这个循环的几个关键特征：

- **多轮**：一个任务可能需要几十次模型调用；
- **可验证**：测试、编译、lint 提供了客观的反馈信号，这是 Agent 相比纯对话的核心优势；
- **状态累积**：前面的修改会改变后续的上下文，因此需要增量式的上下文管理。

代价是延迟从毫秒级变成**几十秒到几分钟**。这意味着 Agent 场景下，用户已经不在"等一个建议"，而是在"等一个结果"。

### 2.2 工具集：越多越难选

Agent 的能力上限由工具集决定。典型工具：

- 读文件、列目录、搜索（grep / 语义搜索）
- 编辑文件（整文件重写、局部补丁、多文件协同修改）
- 执行终端命令（跑测试、编译、安装依赖）
- 浏览器（查文档、看报错页面）

但工具越多，模型选择正确工具的难度越高。这是一个被反复验证的失败模式：**工具集膨胀会导致模型在相似工具之间摇摆，甚至选错工具**。人类在两个功能重叠的工具之间也会犹豫，模型同样如此。

工程上的应对：

- **工具描述要精确且互斥**，避免"查找文件"和"搜索文件"这种语义重叠；
- **给 Agent 一个结构化的仓库地图**（下一节详述），让它不需要靠盲目搜索来定位代码；
- **分层设计**：高频、低风险的操作给 Agent 直接工具；高风险操作走确认流程。

### 2.3 评测：SWE-bench 是唯一硬指标

补全可以用 top-k 准确率近似，但 Agent 的能力很难用离线指标衡量。**SWE-bench** 是目前最受认可的基准。

SWE-bench（[arXiv:2310.06770](https://arxiv.org/abs/2310.06770)，ICLR 2024）的构造方式：

- 从 12 个流行 Python 仓库收集 **2,294 个真实 GitHub issue** 及其对应的上游修复 PR；
- 任务形式：给模型整个代码库 + issue 描述，要求**修改代码库**使相关测试通过；
- 关键特征：需要跨函数、跨类、跨文件的协调修改，而不是写一个独立函数。

论文中当时最强的模型 Claude 2 只解决了 **1.96%** 的实例。这个数字的意义在于：它说明"写代码"和"改一个真实的大型代码库"之间有一条巨大的鸿沟。

**SWE-bench Verified**（[swebench.com/verified.html](https://www.swebench.com/verified.html)）是与 OpenAI 合作的人工筛选版本：从 SWE-bench 中挑出 **500 个实例**，由标注者核对问题描述清晰、测试补丁正确、任务确实可解。它的价值在于排除了原始基准里那些"描述不清"或"测试本身有问题"的噪声样本。

**工程结论**：如果你的 Agent 要在真实仓库里改代码，**resolved rate（解决率）是唯一有意义的硬指标**。任何"模型觉得自己改对了"的自我评估都不可靠，必须跑测试。

### 2.4 沙箱与安全

Agent 会执行代码，这是它和普通聊天机器人最本质的区别，也是最大的风险来源。

必须隔离的维度：

- **文件系统**：Agent 不应能读到仓库外的敏感文件；
- **网络**：默认断网或白名单，防止数据外泄或被诱导下载执行恶意代码；
- **权限**：不要用 root/管理员身份跑 Agent 进程；
- **资源**：限制 CPU、内存、磁盘、执行时长，防止死循环把机器打满；
- **回滚**：所有修改必须可撤销，最好在容器或 git worktree 里执行。

一个务实的做法是：**Agent 在一次性容器里工作，产物只有 diff 会被提交回宿主**。这样即使 Agent 被诱导执行了恶意命令，破坏范围也被限制在容器内。

## 三、上下文检索：让模型看见整个代码库

### 3.1 问题：代码不是自包含的

一个函数可能依赖 10 个文件里的类型定义；一个 bug 的修复点可能藏在 5 层调用之外。**代码的正确理解是跨文件的**，但模型的上下文窗口装不下整个仓库。

这就是编程助手必须做检索的根本原因：不是"让模型读得更多"，而是"让模型读得**更准**"。

### 3.2 repo map：给模型一张地图

**repo map** 是 aider 提出的方案（[aider.chat/docs/repomap.html](https://aider.chat/docs/repomap.html)、[aider.chat/2023/10/22/repomap.html](https://aider.chat/2023/10/22/repomap.html)）：

1. 用 **tree-sitter** 从源文件中抽取符号定义（类、函数、方法）——aider 早期用 ctags，后来换成 tree-sitter，因为后者对多种语言的支持更好、解析更准；
2. 生成一张 map：每个文件列出其中的关键类/函数及其定义行号；
3. 在"文件为节点、依赖为边"的图上做**图排序算法**，只保留被引用最多的标识符；
4. 把这张 map 作为上下文交给模型，并告诉它**可以用搜索工具去展开任何它感兴趣的文件**。

关键设计取舍：

- **默认只给 1k token**（`--map-tokens` 默认值），按当前 token 预算动态裁剪；
- **给地图，不给全文**——让模型自己决定展开哪些文件，而不是替它决定；
- 图排序保证"最重要的符号"优先进入有限的预算。

这个思路的精髓是：**用结构化的压缩代替无差别的截断**。一张 1k token 的地图，可能比 20k token 的随机代码片段更有用。

### 3.3 语义索引：Cursor 的实践

Cursor 在《Securely indexing large codebases》中公开了他们的做法（[prod.cursor.com/blog/secure-codebase-indexing](https://prod.cursor.com/blog/secure-codebase-indexing)，2026-01-27）。几个关键设计：

**用 Merkle tree 做增量同步。** 每个文件算一个加密哈希，每个目录算一个由其子项哈希导出的哈希，整棵树自底向上收敛到根哈希。这样做的直接收益是：**5 万个文件的文件名 + SHA-256 只有约 3.2 MB**，同步整个仓库的"结构"非常便宜，只有内容真正变化的文件才需要重新处理。

**syntactic chunk + embedding。** 文件被切成"句法块"（syntactic chunk）后转成 embedding。这一步很昂贵，因此是**异步后台进行**的，并按 chunk 内容缓存 embedding——同一个 chunk 内容不重复计算。

**simhash 复用相似代码的索引。** Cursor 观察到同一个组织内不同代码克隆之间的相似度平均达到 **92%**。他们用 simhash 在向量库里找最相近的已有索引并直接复用，避免重复 embedding。效果很直接：

| 指标 | 复用前 | 复用后 |
| --- | --- | --- |
| time-to-first-query 中位数 | 7.87s | 525ms |
| p90 | 2.82min | 1.87s |
| p99 | 4.03h | 21s |

**防跨副本泄露。** 用 Merkle 内容证明来确保：一个组织的索引不会被错误地复用到另一个组织的相似代码上。这是"复用"这个优化必须配套的安全措施。

**可用性门槛。** 语义搜索需要索引完成度达到 **80% 以上**才可用——宁可告诉用户"还没索引好"，也不要给出一个基于不完整索引的错误答案。

### 3.4 混合检索：grep + 语义搜索缺一不可

Cursor 在《Improving agent with semantic search》中报告（[prod.cursor.com/blog/semsearch](https://prod.cursor.com/blog/semsearch)，2025-11-06）：

- 在 Cursor Context Bench 上，语义搜索让答题准确率平均 **+12.5%**（随模型不同在 6.5%~23.5% 之间）；
- A/B 测试中，代码留存率 +0.3%（在 1000+ 文件的大库上 +2.6%）；
- 没有语义搜索时，用户不满意的追加请求增加 2.2%；
- **grep + 语义搜索的组合效果最好**，任何单独一种都不够。

为什么两者必须共存：

| 维度 | grep / BM25 | 语义搜索 |
| --- | --- | --- |
| 精确符号（函数名、变量名） | 强 | 弱 |
| 同义表达（"处理超时" vs "timeout"） | 弱 | 强 |
| 跨语言/跨框架概念 | 弱 | 强 |
| 索引滞后时的可靠性 | 高（直接读文件） | 低（依赖索引新鲜度） |
| 延迟 | 低 | 高 |

语义搜索还有一个被低估的工程细节：Cursor 的 embedding 模型是**用 agent 会话轨迹训练**的。具体做法是回放 agent 的搜索与文件打开顺序，用 LLM 判断"哪段内容在当时最有用"，再训练 embedding 去对齐这个排序。这意味着**检索模型本身也是可以从 agent 行为里持续学习的**，而不是一个静态的通用 embedding。

### 3.5 隐私：代码是最敏感的资产之一

代码库索引把"仓库里有什么"变成了一个可被查询的结构化数据。这带来几个必须回答的问题：

- **索引数据存在哪里**？本地、自建服务，还是第三方云服务？
- **谁能查**？跨组织、跨团队的隔离如何保证？
- **索引里有什么**？是否包含了密钥、内部域名、未发布的功能？
- **索引多久过期**？员工离职、项目下线后数据是否删除？

Cursor 的 Merkle 内容证明和 simhash 复用机制，本质上是在回答"**怎么在不泄露 A 组织代码的前提下，复用 B 组织的索引结构**"。这是一个很典型的工程问题：**优化（复用）和安全（隔离）必须同时设计**，事后打补丁很难。

一个务实的建议：**把"索引数据的存储位置和访问权限"当作和"模型选型"同等重要的决策**，在项目初期就定下来，而不是等功能上线后再补。

## 四、工程取舍：延迟、成本与质量

### 4.1 三角关系

编程助手的三种能力，各自有不同的成本结构：

| 能力 | 延迟 | 单次成本 | 质量上限 | 典型模型规模 |
| --- | --- | --- | --- | --- |
| 补全 | 100ms 量级 | 极低 | 中（单文件、局部） | 1.3B~15B |
| Agent | 几十秒~几分钟 | 高（多轮 + 长上下文） | 高（可验证、多步） | 7B~70B+ |
| 检索 | 毫秒~秒级（查询） | 索引成本前置，查询便宜 | 决定前两者上限 | 视方案 |

三者的关系不是"谁替代谁"，而是**串联**：检索给 Agent 和补全提供上下文，Agent 和补全各自服务不同的交互场景。

### 4.2 索引成本是可以摊薄的

语义索引的主要成本在**建索引**，而不在查询：

- embedding 计算昂贵 → 异步后台做，按内容缓存；
- 增量更新 → Merkle tree 只处理变化的文件；
- 复用 → simhash 让相似代码共享索引。

把这些都做对，查询侧就可以做到毫秒级，索引成本被大量查询摊薄。**索引不是一件"一次性任务"，而是一个需要持续维护的后台服务**——它有自己的可用性、新鲜度和成本指标。

### 4.3 一致性：索引永远滞后于代码

代码仓库是高频变更的。任何索引方案都要面对一个事实：**索引一定滞后于代码**。

这带来两类问题：

- **假阳性**：索引里有、代码里已经被删掉的符号，模型会被误导；
- **假阴性**：新加的代码还没进索引，模型"看不见"。

工程上的应对：

- 索引的新鲜度要**可观测**（比如"索引延迟 P95"作为一个指标）；
- 对精确符号（函数名、类名），始终保留 grep 作为兜底，因为它直接读文件、永远新鲜；
- 在 Agent 场景下，让模型在"不确定"时主动去读文件，而不是依赖索引给出的答案。

## 五、落地清单与度量

### 5.1 上线前检查清单

- [ ] 明确区分**补全**与 **Agent** 两条链路，不要共用同一个上下文组装逻辑。
- [ ] 确认补全的**端到端延迟**（含网络、prefill、传输）在 100ms 量级内。
- [ ] 确认补全上下文有**明确的分层裁剪策略**，而不是"文件多大就传多大"。
- [ ] 确认 FIM 请求正确携带了**光标后的后缀内容**。
- [ ] 确认 Agent 在**隔离环境**中执行代码（文件系统、网络、权限、资源限制）。
- [ ] 确认 Agent 的所有修改**可回滚**（容器 / git worktree / 自动备份）。
- [ ] 确认仓库有 **repo map 或等价的结构化地图**，Agent 不靠盲目搜索定位代码。
- [ ] 确认检索是**混合方案**（grep + 语义），且语义索引有明确的新鲜度指标。
- [ ] 确认索引数据的**存储位置、访问权限、保留期限**已定义。
- [ ] 确认有 **SWE-bench 或等价**的端到端评测，而不只是离线 benchmark。

### 5.2 建议监控的指标

| 指标 | 为什么重要 | 建议告警阈值 |
| --- | --- | --- |
| 补全端到端延迟 P95 | 超过 100ms 建议就会"过期" | P95 > 300ms 告警 |
| 补全接受率 | 真实产品指标，比离线准确率更能反映体验 | 环比下降 10% 告警 |
| Agent 任务解决率 | 对应 SWE-bench resolved rate | 任一任务类型下降 5% 告警 |
| Agent 平均轮次 | 轮次暴涨通常意味着模型在原地打转 | 超过基线 2 倍告警 |
| 单次 Agent 任务成本 | 多轮 + 长上下文会让成本失控 | 环比上涨 20% 告警 |
| 索引新鲜度 P95 | 索引滞后会直接导致假阳性 | 超过 5 分钟告警 |
| 语义搜索索引覆盖率 | 低于 80% 时结果不可信 | 低于 80% 时降级并告警 |
| Agent 沙箱逃逸/异常执行次数 | 安全指标 | 任一异常立即告警 |

### 5.3 常见反模式

1. **把补全和 Agent 当成一个系统**：两者的延迟预算差两个数量级，共用上下文策略必然两头不讨好。
2. **只看离线 benchmark 选模型**：top-k 准确率和在线接受率是两回事，必须做真实代码库的 A/B。
3. **索引一次就完事**：代码天天在变，索引是一个需要持续维护的后台服务。
4. **只做语义搜索**：精确符号用 grep 更准，两者必须共存。
5. **给 Agent 一把锤子就让它干活**：没有 repo map，Agent 只能靠盲目搜索定位代码，效率极低。
6. **让 Agent 在宿主机上直接跑命令**：必须隔离，否则一次被诱导的 `rm -rf` 就是事故。
7. **索引到密钥和敏感信息**：建索引前先做敏感信息扫描，不要等问题爆发再补。
8. **忽略许可证**：开源代码模型的许可条款差异很大，选型必须过法务。

## 小结

AI 编程助手的核心是一条生产链路：**补全 → Agent → 检索 → 沙箱**，四者各有不同的成本结构和失效模式。

几条最实用的结论：

1. **补全的本质是 FIM 填空**，不是续写；光标后的后缀和延迟预算（100ms 量级）是补全设计的两个硬约束。
2. **Agent 的本质是可验证的闭环**，SWE-bench 的 resolved rate 是唯一有意义的硬指标；Claude 2 当年只有 1.96%，说明"写代码"和"改真实仓库"之间差距巨大。
3. **检索的本质是给模型一张地图**：repo map 用 1k token 的结构化压缩代替无差别截断；语义索引用 Merkle tree 做增量、用 simhash 做复用，把首次查询从 7.87 秒压到 525 毫秒。
4. **grep 和语义搜索必须共存**：前者保证精确符号和新鲜度，后者保证同义表达和跨概念召回。
5. **安全不是附加项**：沙箱隔离、Merkle 内容证明、索引权限，都必须在架构设计阶段就位。

最后一条建议：**先量延迟，再谈模型**。编程助手的大多数体验问题，最后都归结为"没搞清楚这条链路上每一环的延迟预算"。
