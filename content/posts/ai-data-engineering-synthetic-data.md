## 引言：数据工程的核心矛盾不是"数据不够"，而是"你不知道哪部分数据在拖后腿"

做 AI 应用久了之后，会形成一个非常一致的直觉：**模型效果的天花板不在模型，在数据。** 换成工程语言就是：瓶颈往往在数据管道，而不是训练配置。

但这句话落到实操层面会立刻塌掉，因为它不可执行。"数据不好"是一个没有可操作性的结论——你没法给"不好"定义验收标准，也没法开一张工单说"请把这部分数据变好"。

真正可执行的问题长这样：

- 我的训练集里有多少**近重复样本**？它们在梯度里贡献了几倍的权重？而我完全不知道它们存在。
- 我用模型生成的合成数据补齐长尾场景，多久之后会开始**反噬**——生成数据再喂回训练集，尾部特征逐代消失？
- 我的标注数据里混进了 PII 和有害内容，我的清洗流程**拦截率**是多少，**误杀率**又是多少？没有这两个数，清洗就只是"跑过了"，不是"通过了"。
- 我的数据飞轮转起来了，但每一轮循环都在**放大**同一个偏差——怎么在架构上打断这个正反馈？

本文要把这些问题拆成四个可落地的技术问题：**清洗（cleaning）、去重（dedup）、合成（synthesis）、飞轮（flywheel）**，每个都给出机制、代价、可运行的代码骨架，以及可以直接抄进自己管线的门禁设计。

全文区分三类陈述：

- **已确认**：有论文、官方文档或源码可以直接支撑的机制与数字。
- **工程经验**：业界常见做法，数字随场景变化，需要在自己的流量上验证。
- **待验证**：需要你用自己的数据做实验才能确定的结论。

## 一、数据清洗：把"看起来干净"变成"可验收的干净"

### 1.1 清洗不是一个动作，是一条有顺序的流水线

新手最常见的错误是把清洗当成一步：拿一个过滤器跑一遍，输出即为干净数据。问题在于**清洗动作之间有强依赖，顺序错了会互相破坏**。

一个可用的顺序（工程经验，非论文结论）：

| 阶段 | 动作 | 为什么必须在这个位置 |
| --- | --- | --- |
| S1 | 格式规范化 | 统一编码、空白、全半角、大小写策略，否则后续所有相似度计算都是噪声 |
| S2 | 硬性规则过滤 | 长度、字符集、模板化文案（如"请输入您的意见"），这类样本应当在任何模型介入前先剔除 |
| S3 | PII 检测与脱敏 | 越早越好。后续的语义去重、聚类、标注抽样都可能把 PII 复制到新地方 |
| S4 | 有害内容过滤 | 依赖分类器，放在规范化之后，避免因格式差异导致分类器漏判 |
| S5 | 近重复检测 | 这一步最贵，但它决定了后续所有统计量的可信度 |
| S6 | 质量打分与阈值筛选 | 用打分器做末位淘汰，而不是全局重排 |

关键点在于 S3 早于 S5。**PII 脱敏会改变文本，从而改变近重复判定结果**——两份只差一个手机号的记录，脱敏后会变成完全重复。反过来，如果先做去重再脱敏，则去重逻辑需要处理"带 PII 的相似度"，阈值调不准。

### 1.2 PII 脱敏：识别与脱敏是两个独立子系统

Microsoft Presidio（现已转入 Data Privacy Stack 社区维护）是这个环节的参考实现。它的模块划分很值得借鉴——**analyzer（识别）与 anonymizer（脱敏）彻底分离**：

- Presidio Analyzer：从文本中识别 PII 实体
- Presidio Anonymizer：用不同的 operator 对识别到的实体做脱敏
- Presidio Image Redactor：用 OCR + PII 识别在图片里涂掉敏感文本
- Presidio Structured：处理结构化/半结构化数据中的 PII

其识别手段是混合的：NER（命名实体识别）、正则、基于规则的逻辑，以及带校验和（checksum）的识别器；同时支持接入外部模型作为 Remote Recognizer（例如把 Azure AI Language、Flair、Span Marker、GLiNER、Transformers 包装成外部识别器）。

支持的实体类型包括：信用卡号、姓名、位置、社会安全号码、比特币钱包、美国电话号码、金融数据等。

值得注意的是 Presidio 官方文档里那句警告，我认为它是整个数据工程领域最该被反复引用的一句话：

> 因为它使用的是自动检测机制，没有保证 Presidio 能找到所有敏感信息。因此应当叠加其他系统与防护措施。

这条约束直接推导出两个工程结论：

1. **脱敏不能只有一层。** 正则 + NER + 校验和 + 抽样人工复核，是最低配置。
2. **脱敏必须可度量。** 你需要 Recall（漏了多少 PII）和 Precision（误杀了多少正常内容），而不是"跑过了"。

### 1.3 用 Presidio 做 PII 识别与脱敏：最小可运行骨架

```python
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine
from presidio_anonymizer.entities import OperatorConfig

analyzer = AnalyzerEngine()
anonymizer = AnonymizerEngine()

text = "联系张伟，电话 13800138000，邮箱 zhangwei@example.com"

# 1) 先识别
results = analyzer.analyze(text=text, language="en")
for r in results:
    print(r.entity_type, r.start, r.end, r.score, text[r.start:r.end])

# 2) 再脱敏：可按实体类型指定不同 operator
result = anonymizer.anonymize(
    text=text,
    analyzer_results=results,
    operators={
        "DEFAULT": OperatorConfig("replace", {"new_value": "***"}),
    },
)
print(result.text)
```

工程经验：把这一步做成**批量接口**（Presidio 提供 `batch_processing` 示例与 PySpark 集成），并把 `score` 作为阈值参数暴露出来。不同实体类型的置信度分布差异很大——信用卡号（可校验）可以卡到 0.9+，人名可能只有 0.6，这个阈值不该写死在代码里。

### 1.4 质量打分的落地方式：末位淘汰，不是全局重排

很多团队的错误做法是"给每条数据打一个 0-100 的质量分，然后按分数排序"。问题是这样做会让**分布被拉平**：如果你要的是 Top 10%，那么 60 分和 75 分的数据之间的差别远不如"合格/不合格"这条线重要。

更稳的做法是工程经验式的三段式：

- **硬门禁（Gate）**：不满足即丢弃。如长度不足、格式错误、命中模板词、PII 未脱敏、重复率超阈值。
- **软排序（Rank）**：在通过门禁的集合内排序，用于决定标注预算的分配顺序、合成数据的种子选择顺序。
- **配额（Quota）**：对关键切片做配额约束，避免"全是高质量但全是同一种任务"的数据淹没长尾。

### 1.5 可观测性：数据质量必须变成 SLI

如果数据质量只能靠人肉抽样，那它就不是工程，而是运气。可上线的最小指标集（工程经验）：

| 指标 | 含义 | 采集方式 |
| --- | --- | --- |
| `pii_recall` | 抽检样本中 PII 被拦截的比例 | 人工标注 200~500 条抽样集，比对脱敏前后 |
| `pii_false_positive_rate` | 正常内容被误脱敏的比例 | 同上 |
| `near_dup_ratio` | 近重复样本占全量的比例 | 去重阶段直接统计 |
| `format_error_rate` | 格式/schema 校验失败率 | schema 校验器 |
| `label_agreement` | 双标注一致率 | 抽样复核 |
| `effective_sample_size` | 去重后的有效样本量 | 重复簇折叠后的簇数 |

这些指标要**按数据源切片看**，而不是只看全局均值。一个上亿条的数据集里，整体去重率 5% 看起来很健康，但如果其中 40% 集中在某个来源，那个来源就等于没有增量。

## 二、去重：近重复检测的机制、代价与参数取舍

### 2.1 为什么必须做近重复检测，而不只是精确去重

精确去重（hash 完全相同）只能抓住最表层的重复。真实数据里的重复几乎都是"近重复"：

- 同一个网页被不同站点转载，标题改了几个字
- 同一个客服问答被换了个称呼
- 同一份文档被切分时切出了高度重叠的 chunk
- 模型生成的合成数据里，同一 prompt 的多次采样高度相似

这类样本的危害是**梯度层面的**：它们不增加信息量，但会显著抬高某些模式的权重。后果是模型在训练集上学得很好，在分布外表现崩坏；同时评估集里混进近重复样本时，指标会虚高到无法指导决策。

### 2.2 三种常用相似度：Jaccard、Containment、编辑距离

选错相似度比选错参数更致命。

| 相似度 | 定义 | 适用场景 | 典型陷阱 |
| --- | --- | --- | --- |
| Jaccard | `\|A∩B\| / \|A∪B\|` | 集合规模相近 | 集合大小差异大时严重低估相似度（分母被大集合撑大） |
| Containment | `\|A∩B\| / \|A\|` | 小查询对大语料，例如"这段 query 在语料里出现过吗" | 需要按大小分桶，否则大集合淹没结果 |
| 编辑距离 | `1 - lev(a,b)/max(len)` | 短文本、模板化差异 | O(n·m)，长文本不可用；阈值需要按长度归一化 |

Jaccard 的偏差在 datasketch 官方文档里有非常直观的解释：对于两对集合，交集大小相近，但因为并集大小不同，Jaccard 相似度可能一个很高一个很低——**大集合在 Jaccard 下被系统性惩罚**。如果你在做"短 query 匹配长文档"，用 Jaccard 会系统性漏召回。

### 2.3 MinHash：把集合相似度变成指纹比较

MinHash 的核心思想是：**Jaccard 相似度可以用多个哈希函数的最小值来无偏估计**。

具体做法：把一个集合里的元素经过 `num_perm` 个独立哈希函数，每个函数取最小值，得到一个长度为 `num_perm` 的签名（signature）。两个集合的 Jaccard 相似度，等于它们签名中相同位置的估计比例。

伪代码（`num_perm=128`）：

```python
from datasketch import MinHash

def minhash_of(tokens: set[str], num_perm: int = 128) -> MinHash:
    m = MinHash(num_perm=num_perm)
    for t in tokens:
        m.update(t.encode("utf8"))
    return m

# 估计两段文本的 Jaccard 相似度
est = minhash_of(a).jaccard(minhash_of(b))
```

关键性质：**估计的标准误差随 `num_perm` 增大而减小**，大致是 `O(1/sqrt(num_perm))`。这是后面所有参数取舍的基础。

### 2.4 MinHash LSH：把 O(n) 扫描变成次线性查询

有了签名还不够——如果每次查询都跟所有签名比一遍，复杂度仍是 O(n)。MinHash LSH 的做法是把签名切成 `b` 个 band，每个 band 含 `r` 个哈希值（`b * r <= num_perm`）；只有当两个集合在**至少一个 band 的全部 `r` 个值上都相同**，它们才进入候选集。

由此得到的召回概率曲线是一条 S 形：

```text
P(s) = 1 - (1 - s^r)^b
```

其中 `s` 是真实 Jaccard 相似度。datasketch 官方文档明确指出：构造器会**搜索所有 `(b, r)` 组合**，把这个 S 形跃迁点放在你设定的 `threshold` 上，方法是最小化阈值下方的假正例面积与阈值上方的假负例面积。

实测的参数选择（datasketch 文档给出，`num_perm=128`）：

| threshold | 优化器选出的 `(b, r)` | 含义 |
| --- | --- | --- |
| 0.3 | `(37, 3)` | band 多、每个 band 短 → 敏感，召回高 |
| 0.5 | `(25, 5)` | 默认甜点 |
| 0.7 | `(14, 9)` | band 少、每个 band 长 → 更严格 |
| 0.9 | `(5, 25)` | 极度严格，近乎精确匹配 |

这个表格给出的直觉非常重要：**阈值越高，band 越少越宽**。因为在接近 1 的相似度区间里，只有"多个哈希同时碰撞"才可靠。

### 2.5 `num_perm` 的取舍：准确率与成本的平方根关系

datasketch 文档给出的实测数据（合成语料，阈值 0.5）：

- `num_perm=32` → `(b=8, r=4)`：仍会返回相似度约 0.2 的集合，也会漏掉约 0.8 的集合 —— 曲线很平坦
- `num_perm=128` → `(b=25, r=5)`：明显更好
- `num_perm=512` → `(b=73, r=7)`：曲线非常接近阶跃函数

代价是**线性的**：`num_perm` 翻倍，签名变长一倍，哈希表数量增加，插入变慢，内存占用上升。

工程经验折中表（**待验证**：需在自己的数据上测）：

| 场景 | 建议 `num_perm` | 理由 |
| --- | --- | --- |
| 百万级样本，宽松去重（阈值 0.6~0.7） | 64~128 | 扫描本身成本已可接受，LSH 主要是为了避免全量比对 |
| 千万级以上，精确近重复审计 | 256~512 | 需要接近阶跃的阈值行为 |
| 只做粗筛（后面还有精确校验） | 32~64 | LSH 返回候选，最后用精确相似度复核 |

### 2.6 `weights`：偏袒假负例还是偏袒假正例

这是一个被严重低估的参数。datasketch 的优化器接受 `weights = (false_positive_weight, false_negative_weight)`：

- `(0.1, 0.9)` → 选出 `(b=32, r=4)`，曲线左移：**假阴性（漏掉真重复）少，但假阳性候选多**
- `(0.9, 0.1)` → 选出 `(b=16, r=8)`，曲线右移：**候选精确，但边界上的真重复会被丢弃**

选择依据非常实际：

- 如果候选之后还要做精确复核（用 `MinHash.jaccard` 或原始集合算精确相似度）→ 用 `(0.1, 0.9)`，把召回做高，复核阶段负责收拾精确度。
- 如果每个候选都很贵（比如每个候选要调一次 embedding 模型或一次人工标注）→ 用 `(0.9, 0.1)`，宁少勿多。

另外可以直接用 `params=(b, r)` 绕过优化器自己钉住曲线，此时 `threshold` 和 `weights` 被忽略。

### 2.7 一个必须知道的陷阱：LSH 返回的是候选，不是答案

datasketch 文档明确写道：`query` 返回的是**候选**——所有在某个 band 碰撞到的东西，**且不排序**。因此"需要精确执行阈值的应用，应当对候选做校验"。

这一点在生产中踩坑率极高。一个真实的失败模式是：

1. LSH 阈值设为 0.8，命中一批候选
2. 直接把候选当作重复对删掉
3. 结果：相似度 0.55 的样本被误删（因为 MinHash 估计本身有噪声，尤其在短集合上）

正确流程是：**LSH 做召回 → 精确相似度做裁决**。而且要注意方向性——如果只需要"是否存在重复"，那用估算值 + 保守阈值即可；如果需要统计"重复簇"的规模，那就必须回算精确相似度来构建连通分量。

### 2.8 规模扩展：Redis / Cassandra 存储层与并行插入

datasketch 的 `MinHashLSH` 支持两种外部存储：

- **Redis**：配置 `storage_config={'type': 'redis', 'redis': {'host': ..., 'port': ...}}`，可通过 `basename` 指定键前缀实现多进程共享同一个索引
- **Cassandra**：配置 `storage_config={'type': 'cassandra', 'cassandra': {'seeds': [...], 'keyspace': ..., 'replication': {...}}}`

批量插入要用 **insertion session**，它能显著减少网络调用次数：

```python
from datasketch import MinHash, MinHashLSH

lsh = MinHashLSH(
    threshold=0.8,
    num_perm=128,
    weights=(0.1, 0.9),          # 偏袒召回，配合后置精确校验
    storage_config={
        "type": "redis",
        "redis": {"host": "localhost", "port": 6379},
        "basename": b"dedup_index_v1",
    },
)

with lsh.insertion_session() as session:
    for key, mh in minhashes:
        session.insert(key, mh)
```

两个必须知道的注意点：

1. **在打开 insertion session 期间查询 LSH 会得到不一致结果。** 所以插入与查询必须分阶段，不能流水线化。
2. **Python 3.12+ 装 Cassandra driver 需要额外装 `pyasyncore`**（Python 不再内置 `asyncore`），否则 import 时报 `Unable to load a default connection class`。

对于流式场景，datasketch 还提供 `datasketch.aio.AsyncMinHashLSH`（异步 MongoDB / Redis），以及 `MinHashLSHForest`（支持 top-k 查询，这是 `MinHashLSH` 本身不支持的）。

### 2.9 语义去重：MinHash 抓不到"换了说法"的重复

MinHash 是词袋（bag-of-words）方法，它对语序和多义词无能为力。以下场景它会漏：

- 段落重排
- 同义词替换（"非常重要" → "极其关键"）
- 句式改写但词大部分保留（这个能抓到一部分）

补充分层（工程经验）：

| 层次 | 方法 | 成本 | 抓什么 |
| --- | --- | --- | --- |
| L1 精确 | SHA-256 / 内容 hash | 极低 | 完全相同 |
| L2 词袋 | MinHash / SimHash | 低 | 局部增删、模板填充 |
| L3 语义 | embedding + ANN（见 [向量数据库选型与工程](/posts/vector-database-selection-engineering/)） | 中 | 同义改写、跨语言 |
| L4 任务级 | 同一 prompt 的多次采样聚类 | 中 | 合成数据的自我重复 |

L3 的成本明显高于 L2：一个粗略的规模感是，L2 在百万级语料上可以在单机完成，而 L3 需要真正的向量检索基础设施。

### 2.10 去重的工程决策清单

- 阈值定多少？不要拍脑袋，先做一次分布采样：抽 1000 条，两两算精确 Jaccard，画出分布直方图，把阈值定在分布的空隙处（**待验证**：需在自己的数据上测）。
- 用 Jaccard 还是 Containment？看集合规模差异。规模差异大就用 Containment 或 LSH Ensemble（datasketch 的 `MinHashLSHEnsemble`，源自 Zhu 等人的 VLDB 论文）。
- 短文本怎么办？MinHash 在短集合上方差大，`num_perm` 要加，或直接退化为精确比对（短文本精确比对本来就便宜）。
- 分片还是全局索引？分片会漏掉跨分片的重复。工程经验：按业务维度分片（如按文档 ID 前缀）可接受，但要**单独跑一次全局审计抽样**，量化跨分片重复率。

## 三、合成数据：不是"越多越好"，而是一笔需要算清成本的风险敞口

### 3.1 合成数据的三个典型场景

先说清楚什么时候合成数据是合理的，否则后面所有讨论都是空转（工程经验）：

| 场景 | 合成什么 | 为什么合理 | 主要风险 |
| --- | --- | --- | --- |
| 长尾任务覆盖 | 罕见指令、边缘 case 的 (指令, 输入, 输出) 三元组 | 真实数据里这些 case 出现频率太低，人工标注不划算 | 模型幻觉被固化成"标准答案" |
| 指令能力提升 | 对已有指令做改写、加难度的变体 | 提升指令覆盖度与复杂度 | 难度分布偏移，模型学不会解但学会了装 |
| 隐私替代 | 用合成数据替换含 PII 的真实样本 | 规避合规风险 | 合成数据的分布未必覆盖真实 PII 场景 |

**不该用合成数据的场景**：需要真实世界最新事实、需要长尾专业知识、需要与人交互才能获得的上下文（用户画像、订单历史）。这类场景合成数据只能作为"格式示范"，不能作为事实来源。

### 3.2 Self-Instruct：合成指令数据最经典的流水线

Self-Instruct 论文（arXiv:2212.10560，ACL 2023）的流程分三步：**生成 → 过滤 → 微调**。

具体机制是：用大模型为一系列种子任务生成 instructions（指令）、input（输入）、output（输出）样本，然后**过滤掉无效或相似的样本**，剩下的用于微调原始模型。

论文报告的结果：

- 应用到 vanilla GPT-3（无微调基座）上，在 Super-NaturalInstructions 上取得 **33% 的绝对提升**。
- 与使用私有用户数据 + 人工标注训练的 InstructGPT-001 表现相当。
- 人工评测显示其数据优于现有公开指令数据集，仅落后 InstructGPT-001 **5 个百分点绝对值**。

代码与数据开源在 `github.com/yizhongw/self-instruct`。

这里最值得注意的不是数字，而是**"过滤"这一步的存在**。Self-Instruct 在生成阶段明确要剔除"无效或相似"的样本——这与第二章的去重是同一件事：**合成数据天生自带大量近重复**，不做去重的合成流水线，产出的是一个高重复的训练集。

### 3.3 Evol-Instruct：把指令"演化"成更复杂的指令

WizardLM 论文（arXiv:2304.12244，ICLR 2024）提出 Evol-Instruct：**从初始指令集出发，通过逐步改写，把指令演化为更复杂的指令**。最终混合这些生成的数据微调 LLaMA，得到 WizardLM。

论文中的关键论断：

- 人工评测（复杂度均衡测试集 + Vicuna testset）显示，**Evol-Instruct 生成的指令优于人工撰写的指令**。
- 在高复杂度部分，**WizardLM 的输出优于 OpenAI ChatGPT 的输出**。
- 在 GPT-4 自动评测中，WizardLM 在 29 项技能中的 **17 项达到 ChatGPT 能力的 90% 以上**。

论文还提到一个常被忽略的观察：**人类可能难以产出高复杂度的指令**（humans may struggle to produce high-complexity instructions）。这解释了为什么"用强模型生成难例"这件事有独立价值——它补的不是数量，而是人类标注者天然不会去写的难度区间。

注意 Evol-Instruct 的"改写"过程本身就是一种**故意的分布偏移**：把数据推向更难的区域。这带来一个必然的副作用——如果你的模型容量不足以处理那些难例，训练出来的模型会学会"用复杂的方式把简单问题说复杂"，而不是解决问题。

### 3.4 Flan-T5：指令微调的数据"三个正交维度"

Flan-T5 论文（arXiv:2210.11416）的贡献是系统性地把 instruction finetuning 的收益拆成三个正交维度：

1. **增加任务数量**（扩任务数）
2. **增加模型规模**（扩模型规模）
3. **加入 chain-of-thought 数据**（CoT 数据）

论文的核心数字：**Flan-PaLM 540B 在 1,800 个任务上微调后，比 PaLM 540B 平均高出 9.4%**，达到 **75.2% 的 five-shot MMLU** 分数。同时发布了 Flan-T5 checkpoints。

这三个维度对数据工程的指导意义是：**合成数据最有价值的用途不是"增加条数"，而是"增加任务维度的覆盖"。**

- 增加同分布的条数 → 收益快速饱和（这就是去重章节要解决的问题）
- 增加新任务类型（新的指令模式、新的输出格式、新的推理链模式）→ 收益显著
- 加入 CoT 数据 → 收益显著，但要求输出数据带推理过程

如果你在规划合成数据预算，把钱花在"更多同类样本"上是最低效的用法。

### 3.5 Model Collapse：合成数据反噬的机制

这是合成数据必须严肃对待的原因。Shumailov 等人的论文《The Curse of Recursion: Training on Generated Data Makes Models Forget》（arXiv:2305.17493）系统研究了这个问题。

论文的结论要点：

- 模型生成的内容参与下一轮训练，会造成**不可逆的缺陷**。
- 具体的退化表现是**原始分布的尾部消失**——稀有特征、少数群体表达、小众模式先被抹掉，然后随着轮次推进越来越严重。
- 该现象在 VAE、高斯混合模型（GMM）、大语言模型中均可出现。
- 论文论证了这对所有学习型生成模型是普遍性的，并强调**真实人类交互数据的价值会越来越高**。

"尾部消失"这一点在业务上的含义非常具体：如果你的产品服务长尾用户，那么用生成数据训练出的模型会**系统性地优先服务主流用户**，因为你用于训练的合成数据本身就是从主流分布生成的。

### 3.6 对策：把"新鲜度"和"多样性"变成显式门禁

工程经验式的三层防线：

| 防线 | 做什么 | 对应风险 |
| --- | --- | --- |
| 保留真实数据 | 永远保留一定比例的真实人类数据参与训练，不允许被合成数据完全替换 | 尾部消失 |
| 新颖度门禁 | 合成样本必须通过"与现有语料集的相似度"检查，过于接近则拒绝 | 自我强化 |
| 多样性配额 | 按任务类型、难度、风格分桶统计生成量，避免某桶垄断 | 分布偏移 |

新颖度门禁的伪代码（可落地为 CI 里的一个步骤）：

```python
# 伪代码：新颖度门禁
def novelty_gate(new_sample, corpus_lsh, min_hash, threshold=0.75):
    """返回 True 表示新样本足够新，可以进入训练集。"""
    candidates = corpus_lsh.query(min_hash)
    if not candidates:
        return True
    # 关键：LSH 只负责召回候选，必须用精确相似度裁决
    for cand in candidates:
        exact = min_hash.jaccard(corpus_minhashes[cand])
        if exact >= threshold:
            return False   # 过于接近已有语料，拒绝
    return True
```

这个伪代码里有两个工程细节值得强调：

1. **`query` 返回的候选不排序，也不保证精确**——所以必须有第二层精确校验（见 2.7）。
2. **阈值要随语料库增长而调整**。语料库越大，撞上高相似样本的概率越高。如果不调整阈值，生成量越大越容易被自己的历史产物堵死。

### 3.7 合成数据的成本核算：四项，不只是 token 费用

合成数据的成本远超 API 调用费。完整的成本表（工程经验）：

| 成本项 | 内容 | 常被忽略 |
| --- | --- | --- |
| 生成成本 | API token 费用或本地推理成本 | —— |
| 校验成本 | 去重、事实核对、安全过滤、质量打分 | 常被完全忽略 |
| 存储与版本成本 | 数据集快照、版本管理、可回滚 | 合成数据增长快，存储成本上升快 |
| 机会成本 | 同样的工程资源本可以用在标注真实数据或改进评测上 | **最容易被忽略，也最致命** |

机会成本这一项值得展开。如果合成 10 万条数据的总成本（含校验）高于标注 1 万条真实数据的成本，而两者的效果差距只有几个百分点，那么合成的意义仅在于"覆盖了真实数据完全无法覆盖的长尾场景"。**如果合成数据只是让训练集变大，那它大概率不划算。**

一个可用的判断准则（工程经验）：**先确认你的瓶颈是"长尾场景没有样本"，而不是"样本质量差"或"评测不可信"。** 瓶颈判断错了，投入方向就整个反了——而这恰恰是最常见的误判。

## 四、数据飞轮：把反馈变成数据的闭环工程

### 4.1 飞轮的四个环节

"数据飞轮"这个词被用得很滥，但落到工程上它是一个有明确边界的闭环：

1. **采集（Collect）**：线上行为、用户反馈、人工标注回流
2. **转化（Transform）**：原始日志 → 结构化样本（经过第一、二章的清洗与去重）
3. **训练与上线（Train & Serve）**：模型更新、灰度发布
4. **反馈（Feedback）**：线上表现回流为下一轮的种子数据

关键在于第 4 步回流的**不是原始日志，而是经过第 2 步转化的合格样本**。很多团队"有飞轮"只是因为有回流通道，但回流动的是原始数据，于是每一轮都在往训练集里灌垃圾。飞轮的质量取决于回流通道的**转化率**，而不是流量。

### 4.2 反馈的三种粒度

| 粒度 | 信号 | 转化成本 | 适合场景 |
| --- | --- | --- | --- |
| 显式 | 点赞/点踩、人工纠错、标注修正 | 低，信号强 | 高价值少量样本，优先级最高 |
| 隐式 | 点击、跳过、采纳、编辑距离 | 中，信号弱 | 大规模筛选，产生候选种子 |
| 对抗性 | 攻击样本、越狱尝试、失败案例 | 中高，信号最强 | 安全相关训练集 |

工程经验：**显式反馈的量通常比隐式反馈少几个数量级，但它的信号密度高得多。** 一个常见的错误是把预算平均分配给三种粒度，结果显式反馈这条最有价值的通道被稀释。

### 4.3 从反馈到训练集的转化链

反馈本身不是训练数据，中间必须有一层"转化"，每一步都在丢信息：

```text
原始反馈
  → 过滤（明显噪声、无效操作）
  → 去重（第二章：MinHash / 语义去重）
  → 归一化（转成统一的 (指令, 输入, 输出) 格式）
  → 增强（补齐上下文、构造正反例）
  → 门禁（质量分、PII 检查、安全检查）
  → 训练集版本
```

这里最容易被跳过的是**归一化**和**增强**。原始反馈是"用户把系统输出改成了这样"，它缺少系统当时的输入上下文；而训练需要的是完整的 (输入, 输出) 对。缺了上下文重建，这批数据在训练时就是有偏的。

### 4.4 飞轮的两种典型失效模式

**失效模式一：偏差放大环。** 线上模型在某个群体上表现差 → 用户更少用 → 该群体的数据更少 → 下一轮模型在该群体上更差。这是一个自我强化的正反馈环，打破它的方式是**主动注入**该群体的真实数据（哪怕人工标注成本很高），或者在采样阶段做配额补偿（4.1 里的 Quota 机制）。

**失效模式二：合成自噬环。** 模型生成的合成数据进入训练集 → 训练出的模型与上一代更相似 → 生成的合成数据与上一代更相似 → 多轮之后分布严重坍缩。这就是 3.5 的 Model Collapse 在产品系统里的具体形态。

打破飞轮两种失效模式的架构原则：**飞轮的输入端必须始终有外部真实数据的入口**，而且这个入口的流量不能随轮次下降而自动减少。

### 4.5 数据集版本管理：让飞轮可回滚

飞轮是持续改写训练集的过程，所以**数据集必须版本化**，而且版本要能精确回滚。最低要求（工程经验）：

| 要求 | 实现 |
| --- | --- |
| 每次训练对应一个不可变的数据集快照 | 数据集以版本号（内容 hash 或递增 ID）存储 |
| 快照可完整还原 | 记录每一批样本的来源 ID 与处理版本 |
| 能重建任意历史版本 | 保留原始数据 + 处理流水线的版本配置，而非只保留结果 |
| 训练与数据版本强绑定 | 模型卡里必须写明训练数据版本 |

只保留最终数据集是不够的——一旦发现某批数据有问题，你无法定位它进入了哪些版本，也无法剔除。

### 4.6 飞轮看板与告警

飞轮的健康度必须可观测。工程经验的最小看板与三个关键告警：

| 看板项 | 说明 |
| --- | --- |
| 反馈量与转化率 | 每轮各来源的原始量 → 合格样本量 |
| 数据新鲜度 | 样本进入训练集的滞后时间分布 |
| 合成数据占比 | 训练集中合成 / 真实 / 人工标注的比例与趋势 |
| 分群覆盖度 | 各关键群体在训练集中的样本占比与线上一致性差距 |
| 重复率趋势 | 近重复比例随轮次的变化 |

三个关键告警（工程经验）：

1. **合成占比越界告警**：合成数据占比超过设定上限时告警——这个比例的单调上升是合成自噬环最早的信号。
2. **新鲜度退化告警**：进入训练集的样本平均滞后时间持续上升，说明飞轮转不动了（常见原因：去重把新数据误杀、门禁过严）。
3. **分群覆盖缺口告警**：某群体的训练集占比显著低于其线上流量占比时告警——这是偏差放大环的早期检测。

## 五、端到端检查清单

### 5.1 完整流水线顺序

把三章内容合起来，一条完整的数据流水线的顺序是：

| 步骤 | 动作 | 章节 | 失败时的典型症状 |
| --- | --- | --- | --- |
| S1 | 格式规范化 | 1.1 | 相似度计算全乱 |
| S2 | 硬性规则过滤 | 1.1 | 模板文案污染指标 |
| S3 | PII 识别与脱敏 | 1.2 / 1.3 | 合规风险 |
| S4 | 有害内容过滤 | 1.1 | 安全隐患 |
| S5 | 近重复检测（精确 + 词袋 + 语义） | 第二章 | 指标虚高、分布外崩溃 |
| S6 | 质量打分与门禁 | 1.4 | 长尾被淹没 |
| S7 | 合成数据新颖度门禁 + 多样性配额 | 3.6 | 分布坍缩 |
| S8 | 版本快照与元数据登记 | 4.5 | 无法回滚、无法定位问题 |

顺序上有两个不可交换的点：**S3 必须在 S5 之前**（脱敏改变文本会改变去重结果），**S7 必须在 S8 之前**（快照要包含门禁后的最终集合）。

### 5.2 CI 门禁验收表

把质量要求做成 CI 里的可执行检查，而不是靠人记住：

| 检查项 | 实现方式 | 失败动作 |
| --- | --- | --- |
| 日期与 front matter 正确 | 脚本校验字段与当天日期 | 阻断提交 |
| PII 残留扫描 | 用 analyzer 扫描全部样本，任一命中即失败 | 阻断提交 |
| 近重复率超阈值 | LSH 统计重复率，超过阈值失败 | 阻断提交 |
| 合规：毒性内容 | 分类器扫描 | 阻断提交 |
| 合成数据占比超限 | 统计合成样本比例 | 阻断提交 |
| 训练/评估集泄漏 | 跨集合近重复检测 | 阻断提交 |

最后一项尤其重要：评估集里混进训练集的近重复样本，是最容易被忽略、且对决策影响最大的问题——它会让你的所有模型对比结论失效。

### 5.3 常见误区速查表

| 误区 | 后果 | 正确做法 |
| --- | --- | --- |
| 清洗当成一步 | 动作间互相破坏 | 按 S1–S6 顺序，且脱敏早于去重 |
| 只做精确去重 | 近重复占比高，指标虚高 | 分层去重 L1–L4 |
| 把 LSH 候选当答案 | 误删中等相似度样本 | LSH 召回 + 精确相似度裁决 |
| 合成数据越多越好 | 分布坍缩、长尾消失 | 新颖度门禁 + 配额 + 保留真实数据 |
| 质量分排序代替门禁 | 分布被拉平 | Gate / Rank / Quota 三段式 |
| 数据质量靠抽样看 | 问题发现太晚 | 质量指标进 SLI，按来源切片 |
| 飞轮只有回流没有转化 | 每轮灌垃圾 | 回流必须经过完整转化链 |
| 数据集不版本化 | 无法定位、无法回滚 | 不可变快照 + 强绑定 |

### 5.4 四个主题的一句话总结

| 主题 | 核心结论 |
| --- | --- |
| 清洗 | 清洗是有顺序的流水线，脱敏必须早于去重，质量必须可度量 |
| 去重 | 近重复比精确重复危险得多；MinHash/LSH 的参数是"召回率 vs 成本"的交易，LSH 只给候选 |
| 合成 | 合成数据的价值在"任务维度覆盖"而非"数量"；必须显式管理崩塌风险 |
| 飞轮 | 飞轮的质量取决于回流转化率而非流量；必须始终保留真实数据入口 |

## 小结

回到引言的那句话：数据工程的难点不在"获取数据"，而在"知道自己有什么数据"。本文的四章其实是同一件事的四个侧面：

- **清洗**让数据的"脏"变成可测量的指标（Recall / Precision / 重复率 / 有效样本量）。
- **去重**让数据的"多"变成真实的"有效样本量"——这是所有后续统计量的前提。
- **合成**让数据的"缺"变成可控的长尾补充，但必须显式管理新颖度与崩塌风险。
- **飞轮**让数据的"新旧"变成一个可回滚、可观测、不会自我强化的闭环。

如果你只带走三件事：

1. **先建指标，再建流水线。** 没有 `pii_recall`、`near_dup_ratio`、`effective_sample_size` 这几个数，任何数据决策都是赌博。
2. **去重用 LSH 召回 + 精确裁决两段式。** 这是 MinHash/LSH 最容易被忽略、也最容易造成数据误删的细节。
3. **合成数据的预算应该花在"新任务类型"上，而不是"更多同类样本"。** 同时永远保留真实数据的入口，否则飞轮会吃掉自己。

最后提醒一句：本文所有参数建议（阈值、`num_perm`、配额比例、告警阈值）都是**工程经验**，不是通用最优解。真正该做的是：拿一批你自己的数据，把第二章 2.10 节说的分布采样跑一遍，让参数从你的数据里长出来，而不是从别人的博客里抄过来。
