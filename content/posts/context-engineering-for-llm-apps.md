## 引言：你可能早就遇到过这些问题

- 同一个模型，短对话里表现很好，会话一长就开始"忘事"、答非所问、重复已经说过的话。
- 一次 Agent 调用烧掉十几万输入 token，其中绝大部分是上一轮已经发过的内容。
- 给 Agent 加了更多工具之后，它反而更容易选错工具，或者在两个相似工具之间反复摇摆。
- 把整个代码库塞进上下文，指望模型"什么都看到"，结果它连最简单的问题都答错了。
- 上下文窗口从 4K 涨到 128K、1M，但任务成功率并没有同步上涨。

这些问题的共同根源，不是"提示词写得不够好"，而是**上下文从来没有被当作一个工程对象来管理**。

过去几年我们一直在优化"怎么把指令写清楚"，这在单次问答场景下是有效的。但 Agent 不是单次问答：它要在几十轮、上百轮推理里持续工作，上下文里同时装着系统提示、工具定义、外部数据、消息历史、工具返回结果。当上下文的规模从几百 token 涨到几十万 token，问题的性质就变了——它不再是措辞问题，而是**资源分配问题**。

这就是上下文工程（context engineering）要解决的事。

## 一、从「写提示词」到「管理上下文」

### 1.1 提示词工程的边界

提示词工程（prompt engineering）关注的是如何编写和组织 LLM 指令以获得最优结果，它的隐含前提是**任务是一次性的**：一个输入，一个输出，上下文里只有指令和输入。

Agent 打破了这个前提。一个运行中的 Agent，上下文里至少有五类内容：

- 系统指令（角色、规则、输出格式）
- 工具定义（名称、描述、参数 Schema）
- 外部数据（检索结果、文件内容、API 返回）
- 消息历史（用户说过的话、模型说过的话）
- 工具调用与返回结果

这些内容会随着轮次不断累积、变化、互相覆盖。**提示词工程只优化了其中很小的一部分。**

### 1.2 上下文工程的定义

Anthropic 在《Effective context engineering for AI agents》给出的定义是：

> 上下文工程是一组策略，用于在 LLM 推理过程中策划并维护最优的 token 集合，包括所有可能进入上下文的其它信息。

Andrej Karpathy 的表述更精炼：

> 上下文工程是"在上下文窗口里，为下一步填入恰好的信息"这门微妙的艺术与科学。

LangChain 则用了一个更工程化的类比：LLM 像操作系统，上下文窗口像 RAM，上下文工程就是内存管理——决定什么留在内存里、什么换出、什么按需调入。

三个定义指向同一件事：**上下文是需要主动管理的有限资源，而不是提示词的附属品。**

### 1.3 为什么这个转变发生在现在

三个条件同时成熟：

- **模型足够强**：推理和工具调用能力足够好，Agent 形态才成立，多轮长时程任务才成为常态。
- **上下文窗口足够大**：从 4K 到 128K 再到 1M，"把一切都塞进去"在技术上成为可能——也正因如此，"塞进去"的诱惑变大了。
- **成本压力足够真实**：长上下文直接反映在账单上。一个 30 轮的编码 Agent 会话，累计输入 token 可以达到百万级。

窗口变大解决的是"装得下"，没有解决"装得对"。

## 二、上下文是一笔有限预算

### 2.1 context rot：长上下文不是免费的

Chroma 的研究团队提出了 **context rot**（上下文腐烂）这个概念：随着上下文窗口里的 token 数量增加，模型从中准确召回信息的能力会下降。

这个现象有两个关键特征：

- **它是渐变，不是断崖**。模型在长上下文里并没有"崩坏"，只是精度下降。Anthropic 的表述是"performance gradient rather than a hard cliff"。
- **它普遍存在**。不同模型的衰减速度不同，但所有模型都有这个特征。

这意味着"上下文窗口 1M"不等于"1M  token 都同样可靠"。把信息放进去，和模型能用好这些信息，是两件事。

### 2.2 attention budget：为什么会有这个现象

Anthropic 把原因归结为**注意力预算**（attention budget）。

Transformer 架构让每个 token 都能 attend 到前面所有的 token，n 个 token 就有 n² 个两两关系。上下文越长，模型要处理的成对关系越多，注意力就被摊得越薄。

此外还有两个因素：

- **训练分布偏差**：训练数据里短序列比长序列常见得多，模型对长程依赖的专项参数更少。
- **位置编码插值**：用插值把模型扩展到比训练时更长的序列是可行的，但对位置的理解会有损失。

结论：**上下文必须被当作边际收益递减的有限资源**。每多放一个 token，都在消耗预算，也都在稀释其余 token 的权重。

### 2.3 上下文窗口里到底装了什么

以一个 200K 窗口的 Agent 会话为例，各部分的典型规模：

| 组成部分 | 典型 token 数 | 每轮是否变化 | 说明 |
| --- | --- | --- | --- |
| 系统提示 | 2,000 ~ 8,000 | 否 | 角色、规则、输出格式约定 |
| 工具定义 | 1,500 ~ 15,000 | 否 | 单个工具约 80~400 token，工具多了很占地方 |
| few-shot 示例 | 0 ~ 4,000 | 否 | 精选示例，不是边界案例清单 |
| 检索到的知识 | 0 ~ 20,000 | 是 | RAG 预取或运行时按需加载 |
| 消息历史 | 0 ~ 100,000+ | 是 | 持续累积，是最需要主动管理的部分 |
| 工具返回结果 | 0 ~ 30,000 | 是 | 最容易爆炸的部分，一次大查询能顶掉半个窗口 |

注意最后一行：**工具返回结果是上下文膨胀的主要来源**。一个 `grep` 返回 5,000 行、一个 API 返回完整 JSON、一次文件读取读了整个大文件——这些都很常见。

### 2.4 一个可执行的预算分配示例

假设窗口 200K，给一个编码 Agent 做预算：

| 用途 | 预算 | 理由 |
| --- | --- | --- |
| 系统提示 + 工具定义 | ≤ 20K | 静态，一次写好，尽量精简 |
| 长期记忆 / 项目约定 | ≤ 10K | 稳定，跨会话复用 |
| 检索到的知识 | ≤ 30K | 按任务相关性裁剪，不要整库塞入 |
| 工作记忆（本轮目标、计划、笔记） | ≤ 20K | 由 Agent 自己维护 |
| 消息历史 | ≤ 110K | 接近上限时触发压缩 |
| 预留缓冲 | ≥ 10K | 给工具返回结果留余地 |

这个数字不是标准答案，但它表达了一个原则：**先给每类上下文定上限，再让内容去适应上限**，而不是让上下文自然膨胀到撑爆窗口。

## 三、结构化输入：让每一类上下文各就各位

### 3.1 系统提示的「高度」

Anthropic 用"高度"（altitude）来描述系统提示的抽象层级，两个极端都会失败：

- **太高**：把复杂的 if-else 逻辑硬编码进提示词，指望精确控制 Agent 行为。结果是脆弱、难维护，模型一改就崩。
- **太低**：给一些笼统的高层指导，或者错误地假设模型和自己有共享上下文。结果是没有可执行的信号。

正确的高度在中间：**具体到能有效指导行为，又灵活到能给模型留下启发式空间**。

一个实用的起步方法：先用最小提示词配合最好的模型跑一遍任务，然后根据实际失败模式逐步补指令和示例，而不是一开始就写一份大而全的提示词。

### 3.2 分段与标记

推荐把系统提示组织成明确的区块，例如：

```text
<background_information>
  项目背景、约束、已知事实
</background_information>

<instructions>
  必须遵守的行为规则，按优先级排列
</instructions>

## Tool guidance
  什么时候该用哪个工具，工具的常见误用

## Output description
  输出格式、字段含义、示例
```

XML 标签或 Markdown 标题都可以。Anthropic 也提到，随着模型变强，具体格式的重要性在下降，但结构化本身仍然是低成本、高收益的做法——它同时帮助人和模型理解上下文的组织方式。

### 3.3 工具定义是上下文的大头

工具定义由名称、描述和参数 Schema 组成，看起来不起眼，实际上很占 token，而且**工具数量的边际成本很高**。

Anthropic 观察到的最常见失败模式是**工具集膨胀**：工具覆盖的功能太多，或者多个工具功能重叠，导致模型在"该用哪个"上产生歧义。

他们给了一个判断标准：

> 如果一个人类工程师都无法明确说出某个场景该用哪个工具，那 AI Agent 也做不到。

对应的工程做法：

- **最小可行工具集**：只保留当前任务真正需要的工具。
- **功能不重叠**：两个工具的适用场景必须有清晰边界。
- **描述写"什么时候用"**：不要只写"做什么"，要写"在什么条件下应该选我"。
- **按需检索工具**：工具特别多时，用检索的方式只把相关工具的描述放进上下文（tool RAG）。

### 3.4 few-shot 示例的取舍

few-shot 示例是有效的，但常见的错误是**堆边界案例**：把每一种可能的例外都写成一个示例，指望模型记住所有规则。

Anthropic 的建议是反过来：精选一组**多样化、典型**的示例，让它们有效传达期望行为。他们的说法是，对 LLM 来说，示例是"值一千字的图"。

判断标准：**一个示例如果只是重复某条文字规则，它就是冗余的**；如果它展示了规则在模糊场景下的应用，它才有价值。

### 3.5 结构化输入检查清单

- [ ] 系统提示是否分块，每块职责单一？
- [ ] 是否存在硬编码的 if-else 逻辑可以下沉到代码或工具里？
- [ ] 工具集是否最小？有没有功能重叠的工具？
- [ ] 每个工具的描述是否说明了"什么时候用"？
- [ ] few-shot 示例是否精选，而不是边界案例清单？
- [ ] 静态内容（系统提示、工具定义）是否放在上下文最前面？
- [ ] 是否避免了把时间戳、随机 ID 放进静态部分（会破坏缓存，见第四章）？

## 四、缓存：把重复的前缀变成便宜货

### 4.1 前缀缓存的工作原理

要理解缓存，先要理解 LLM 推理的两个阶段：

- **Prefill（预填充）**：读取所有输入 token，为每个 token、每一层计算一个 key 向量和 value 向量，也就是 **KV cache**。这是计算密集阶段。
- **Decode（解码）**：一个 token 一个 token 地生成输出，每生成一个就 attend 到 KV cache。

对一个编码 Agent 来说，每一轮都要把之前所有的对话重发一遍。第 30 轮时，输入里可能有 6 万 token，其中 5.85 万是前面发过的。

**前缀缓存就是复用已经算好的 KV cache**：如果新请求的开头与某个之前的请求完全一致，那么这部分 token 可以跳过 prefill，并且按折扣价计费。

### 4.2 三条铁律

**铁律一：精确前缀匹配。**

注意力机制决定了位置 n 的 token 的 cache 依赖于它前面的所有 token。所以只有从第 0 个 token 开始、直到第一个不同 token 之前的部分，才能命中。一个字节不同，后面全部失效。

**铁律二：块对齐。**

推理引擎不是按 token 存 cache 的，而是按固定大小的块（block）存，并对整块做哈希。

- vLLM 默认 16 个 token 一个块，用链式哈希：块 0 的哈希只覆盖自己，块 1 的哈希覆盖块 0 的哈希加自己，依此类推。这样只要块 N 的哈希匹配，就能保证前面所有块都一致。
- SGLang 用基数树（radix tree）存同样的东西，共享前缀合并成一个节点，淘汰时从叶子往里做 LRU。

后果是：**很短的提示词没有完整的块可以复用**，所以各家都规定了最小可缓存长度。

**铁律三：本地性。**

cache 存在于跑那次 prefill 的 worker 的 GPU 内存里（有时会分层到 CPU 或 NVMe）。请求只有被调度到同一个 worker、且块还在，才能命中。保留时间由 TTL 或 LRU 淘汰决定。

第三条意味着：**命中率是一个调度问题，不只是一个开关问题**。如果你的网关或路由器每轮都重新选一次后端，缓存就废了。

### 4.3 各家规则差异

机制相同，但写入是否收费、保留多久、最小长度、是否需要显式开启，各家不一样。下表是 2026-09 的第三方汇总（以各家官方文档为准）：

| 厂商 | 是否需显式开启 | 写入是否额外收费 | 读取折扣 | 保留期 | 最小前缀 |
| --- | --- | --- | --- | --- | --- |
| Anthropic | 需要（cache_control 断点） | 是，5 分钟 TTL 收 1.25x，1 小时 TTL 收 2x | 约 0.1x | 5 分钟默认，可选 1 小时，命中即刷新 | 1,024 token |
| OpenAI | 自动 | 否 | 约 0.1x | 约 30 分钟 | 1,024 token |
| Google Gemini | 隐式自动 + 显式 CachedContent | 隐式不收费；显式按存储时长计费 | 约 0.1x | 隐式按最近请求；显式自定义 | 4,096 token（隐式） |
| DeepSeek | 自动 | 否 | 低于 0.1x（官方文档未给具体倍数） | 不用后数小时到数天自动清空 | 完整前缀匹配，间隔未公布 |

DeepSeek 的官方文档还补充了几个细节：缓存前缀以"完整单元"为单位匹配；每次请求的**用户输入结束位置**和**模型输出结束位置**都会各产生一个缓存前缀单元；系统检测到多次请求的公共前缀时也会单独落盘；长输入会按固定 token 间隔截取落盘，避免长前缀一直达不到结束位置而完全无法被缓存。

### 4.4 为什么缓存会失效

生产环境里缓存命中率突然掉下去，通常是这几个原因：

- **前缀里改了东西**。最常见的是在系统提示里塞了当前时间、请求 ID、随机数。第一个块一变，从第 0 个 token 开始就全不命中。
- **换了模型**。每个模型有自己独立的 cache，换模型等于全部重新 prefill。
- **换了 worker**。请求被路由到另一台机器，本地性失效。
- **超过 TTL 或被 LRU 淘汰**。
- **工具定义变了**。工具定义位于上下文前部，它一变，后面全部失效。

最后一条特别值得注意：**工具定义的变更会连带失效**，即使系统提示本身没变。所以工具集应该保持稳定，不要每轮动态增删。

### 4.5 提高命中率的写法

- **静态在前，动态在后**。系统提示、工具定义、长期记忆放最前面；时间戳、会话 ID、本轮变量放最后。
- **不要往静态区塞变量**。如果确实需要时间，把它放在消息里，不要放在系统提示里。
- **保持工具定义稳定**。能复用就不要重建。
- **保持路由粘性**。用固定 session、固定 API key 或网关侧的 sticky routing，让同一会话落到同一后端。
- **看 usage 字段**。Anthropic 返回 `cache_read_input_tokens` / `cache_creation_input_tokens` / `input_tokens`，DeepSeek 返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。命中率是上下文工程最直接的量化指标。

### 4.6 一个成本测算示例

假设某模型输入价格 $2.00 / 1M token，缓存读取 $0.20 / 1M token（0.1x），缓存写入溢价 1.25x。

场景：30 轮会话，固定前缀 20,000 token（系统提示 + 工具定义），每轮新增 1,500 token。

```text
累计 prompt token = 30 * 20000 + 1500 * (0 + 1 + ... + 29)
                  = 600000 + 1500 * 435
                  = 1,252,500
```

| 方案 | 计算 | 成本 |
| --- | --- | --- |
| 完全不缓存 | 1,252,500 x $2.00 / 1M | $2.505 |
| 90% 命中 | 125,250 x $2.00 + 1,127,250 x $0.20（单位 /1M） | $0.476 |
| 95% 命中（精确重放） | 62,625 x $2.00 + 1,189,875 x $0.20（单位 /1M） | $0.363 |

90% 命中相比不缓存下降约 81%。

写入溢价的影响：首次写入 20,000 token 按 1.25x 计，相当于多付 5,000 token 的价钱，即 $0.01。而一次命中省下的钱远超这个数——**只要会被复用一次，写入溢价就是值得的**。

注意这个例子里输出 token 没有被缓存影响。如果 Agent 的输出占比很大（比如带长推理链的模型），缓存只能砍输入那一行，砍不到输出那一行。

## 五、压缩：把长对话折起来

### 5.1 compaction：最主流的一招

**compaction（压缩）** 指的是：当对话接近上下文窗口上限时，把内容总结成摘要，然后用摘要重新开启一个上下文窗口。

Anthropic 描述的 Claude Code 实现方式是：把消息历史交给模型做总结和压缩，保留架构决策、未解决的 bug、实现细节，丢弃冗余的工具输出和消息；然后 Agent 带着压缩后的上下文**加上最近访问的 5 个文件**继续工作。

他们特别强调了 compaction 的取舍艺术：

> 过于激进的压缩会丢失微妙但关键的上下文，而这些上下文的重要性往往要到之后才显现。

实践建议：**先最大化召回，再提升精度**。压缩提示词应该先保证抓住所有相关信息，然后反复迭代去掉多余内容。

### 5.2 工具结果清理：最轻量的一档

一个安全的、最轻量的压缩形式是**清理工具调用和原始结果**。

理由很直接：一个工具调用已经深埋在历史里，模型还需要再看一次原始返回吗？通常不需要——它需要的是那次调用的**结论**。

Anthropic 把这个能力做成了平台侧的功能（tool result clearing，随 context management 一起发布）。它的价值在于：不需要模型参与总结，纯粹是确定性的裁剪，没有信息损失风险。

### 5.3 结构化笔记

**结构化笔记**（structured note-taking / agentic memory）是让 Agent 定期把笔记写到上下文窗口之外，之后再拉回来。

典型形态：

- Claude Code 的 todo list
- 自定义 Agent 维护的 `NOTES.md`
- 平台侧的 memory tool（文件式，公开测试版）

Anthropic 举了 Claude playing Pokémon 的例子：Agent 在几千步游戏过程中持续维护精确的计数（"过去 1,234 步我在 1 号道路练级，皮卡丘升了 8 级，目标是 10 级"）、探索过的区域地图、关键成就、有效的战斗策略。上下文重置后，它读自己的笔记，继续跨小时的训练流程。

关键点：**笔记的价值在于它是 Agent 自己写的**，所以格式和内容天然贴合它后续的需要。

### 5.4 子 Agent 隔离

**子 Agent 架构**解决的是另一个问题：让一个 Agent 保持干净上下文，而把"大量探索"外包出去。

做法：主 Agent 持有高层计划，子 Agent 处理聚焦任务。每个子 Agent 可以用掉几万 token 做深入探索，但**只返回一份精炼的摘要**——Anthropic 说这个摘要通常在 1,000~2,000 token。

这实现了清晰的关注点分离：详细的搜索上下文被隔离在子 Agent 里，主 Agent 专注于综合和分析。Anthropic 的多 Agent 研究系统在这个模式下，复杂研究任务的表现显著优于单 Agent。

### 5.5 四种策略怎么选

| 策略 | 适合的场景 | 代价 |
| --- | --- | --- |
| compaction | 需要大量来回、保持对话连续性的任务 | 需要调压缩提示词，有信息损失风险 |
| 工具结果清理 | 工具输出很多、且结论已提取 | 几乎无代价，确定性裁剪 |
| 结构化笔记 | 有明确里程碑的迭代式开发 | 需要 Agent 自律维护 |
| 子 Agent | 复杂研究、需要并行探索 | 需要编排，摘要可能丢细节 |

实践里通常是组合使用：工具结果清理兜底，结构化笔记跨轮次保持状态，compaction 在接近窗口上限时触发，子 Agent 处理需要大量探索的子任务。

## 六、运行时检索：just-in-time

### 6.1 预取 vs 按需

当前主流的两种上下文供给方式：

- **预取（pre-inference retrieval）**：推理前用 embedding 检索，把相关上下文塞进提示词。RAG 是典型。
- **按需（just-in-time）**：只保留轻量标识符——文件路径、存储好的查询、网页链接——运行时用工具把数据加载进来。

Claude Code 是后者的代表：模型可以写针对性的查询、存结果、用 `head` / `tail` 这类命令分析大量数据，**而从不把完整数据对象放进上下文**。

### 6.2 渐进式披露

按需检索的核心思想是**渐进式披露**（progressive disclosure）：Agent 通过探索逐步发现相关上下文，每一步交互产生的上下文指导下一步决策。

Anthropic 指出，这里的信号不仅来自内容本身：

- 文件大小暗示复杂度
- 命名约定暗示用途（`tests/test_utils.py` 和 `src/core_logic/test_utils.py` 是两回事）
- 时间戳可以作为相关性的代理

所以 Agent 可以一层层组装理解，只在工作记忆里保留必要的内容。

### 6.3 混合策略

按需检索的代价是**比预取慢**，而且需要精心设计工具和启发式，否则 Agent 会用错工具、走死路。

所以实践中常见混合：

- **静态内容预取**：项目约定（如 `CLAUDE.md`）直接放进上下文，保证速度。
- **动态内容按需**：用 glob、grep 这类原语让 Agent 自己探索，避免索引过期和语法树复杂度。

Anthropic 的建议是：**做能跑通的最简单的事**（do the simplest thing that works）。

## 七、落地清单与度量

### 7.1 上下文工程检查清单

**输入结构**

- [ ] 静态内容在前、动态内容在后
- [ ] 系统提示分块、职责单一、无硬编码 if-else
- [ ] 工具集最小、功能不重叠、描述写明"何时用"
- [ ] few-shot 示例精选，不是边界案例堆砌

**缓存**

- [ ] 静态区不含时间戳、随机 ID、会话 ID
- [ ] 工具定义跨轮次稳定
- [ ] 路由有粘性，同一会话落到同一后端
- [ ] 监控 `cache_read_input_tokens` / `prompt_cache_hit_tokens`

**压缩**

- [ ] 有明确的 compaction 触发阈值（如窗口 80%）
- [ ] 压缩提示词先保证召回，再压精度
- [ ] 工具结果清理作为兜底
- [ ] 有结构化笔记机制承载跨轮次状态

**长时程**

- [ ] 超过窗口 1/3 的任务考虑子 Agent 隔离
- [ ] 子 Agent 返回摘要长度有上限
- [ ] 有"做通的最简单方案"，而不是一上来就全套

### 7.2 该度量什么

| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| 缓存命中率 | 命中 token / 总输入 token | 直接对应成本，也反映上下文是否稳定 |
| 单轮平均上下文长度 | 每轮输入 token 均值 | 反映膨胀速度 |
| 每任务 token 成本 | 完成一个任务的总输入 token | 比单次成本更有意义 |
| 工具选择准确率 | 选对工具的比例 | 反映工具集设计质量 |
| 长上下文任务成功率 | 与短上下文基线对比 | 反映 context rot 的实际影响 |
| 压缩触发次数 | 单位任务触发 compaction 的次数 | 反映预算分配是否合理 |

其中**缓存命中率是最划算的单一指标**：它同时衡量了上下文结构（静态/动态是否分离）、路由稳定性和成本。命中率突然下降，通常意味着前缀被污染了。

### 7.3 反模式

- **把整个代码库塞进上下文**：窗口装得下不等于模型能用好，通常会让表现变差。
- **在系统提示里塞时间戳**：一次变动让整段缓存失效。
- **每轮重建工具定义**：工具定义在上下文前部，重建会导致后面全部重新 prefill。
- **给模型所有工具**：工具越多，选择越难，上下文越贵。
- **把 compaction 当成免费操作**：压缩是有信息损失的，取舍需要调。
- **只看单次调用成本**：Agent 的成本是累计的，30 轮会话的输入 token 是单轮的几十倍。
- **忽略输出侧成本**：缓存只影响输入，长推理链的成本要单独优化。

## 小结

上下文工程是提示词工程的自然延伸：当任务从"一次问答"变成"多轮长时程 Agent"，上下文就从提示词的附属品变成了需要主动管理的有限资源。

三条主线：

- **结构化输入**：把系统提示、工具定义、示例、历史各就各位，静态在前动态在后，工具集保持最小。
- **缓存**：理解精确前缀匹配、块对齐、本地性三条铁律，让静态部分稳定下来，把重复成本打掉。
- **压缩**：compaction 保持长时程连贯性，工具结果清理做确定性兜底，结构化笔记承载跨轮次状态，子 Agent 隔离大量探索。

最核心的判断标准只有一句：**找到能最大化期望结果的最小高信号 token 集合**。窗口变大不会自动让这句话变得更容易，只会让"什么都塞进去"变得更有诱惑。
