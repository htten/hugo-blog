## 引言：为什么工程师必须理解模型内部

很多人用大模型的方式停留在「写提示词、拿到 JSON、解析结果」。这种用法在 demo 阶段足够，但一旦进入生产，问题会立刻变得具体而尖锐：

- 为什么同样的 prompt 换个模型就崩了？
- 为什么输入长了之后延迟不是线性增长，而是突然爆炸？
- 为什么开了流式输出反而更慢、更贵？
- 为什么厂商说「128K 上下文」，你的任务却在 8K 就开始遗忘？
- 为什么 max_tokens 调大反而让回答变差？

这些问题的答案都不在提示词工程里，而在模型与推理引擎的内部机制里。理解这些机制，才能把「模型能力」翻译成「系统能力」——在延迟、成本、稳定性、可复现性四个维度上做出可预测的工程决策。

本文按数据流的顺序，把现代大语言模型从文本输入到 token 输出的全过程拆开讲一遍：先看模型怎么读文本，再看它怎么算，再看它怎么被训练出来，最后看它在生产环境里怎么跑。

## 一、从文本到 Token：一切始于离散化

神经网络不能直接处理字符串，模型看到的第一个东西是一串整数：token ID。

### 1.1 分词器的选择与代价

主流做法是 BPE（Byte Pair Encoding）及其变体：先从字节级词表出发，统计语料中最高频的相邻符号对，反复合并，直到词表达到目标规模。GPT-4 一类的闭源模型使用约 10 万量级的词表，Llama 3 使用 128K 词表，中文场景下词表大小直接影响「一个汉字占几个 token」。

这里有一个直接影响成本与延迟的工程结论：**词表越大，同一段文本的 token 数越少，输入输出成本越低，但词表本身会带来模型参数开销与长尾 token 的低频问题**。一个 128K 词表的模型，罕见汉字往往只占 1 个 token；而小词表模型可能把它切成 3～4 个，prompt 成本直接翻倍。

### 1.2 Token 边界不是语义边界

实践中一个常见坑是：模型看到的是 token 序列，不是字符序列。这会导致两类错误。

```text
输入："2026年11月6日"
小词表切分: ["202", "6", "年", "11", "月", "6", "日"]   → 7 token
大词表切分: ["2026", "年", "11", "月", "6", "日"]        → 6 token
```

更麻烦的是「看起来是同一个词、切出来不一样」的情况。例如 `New York` 可能被切成 `New` + ` York`，而 `NewYork` 是一个完整 token；`Ġ`（前导空格标记）这类字节级编码符号还会在可视化时污染输出，调试时看到满屏 `Ġ` 和 `Ċ` 就知道自己在看原始 token。

### 1.3 缓存友好的提示词布局

推理引擎普遍提供 prefix caching（KV cache 前缀复用）：如果多次请求的 prompt 前若干 token 完全相同，这部分 KV 不会重算。因此把**稳定不变的内容放前面、变化的内容放后面**是硬性优化手段：

```text
❌  [用户问题] + [系统提示] + [few-shot 示例]   ← 前缀每次都变，缓存全部失效
✅  [系统提示] + [few-shot 示例] + [用户问题]   ← 前缀稳定，命中缓存
```

在 RAG 场景里，系统提示 + 检索到的文档顺序同样重要：若检索结果排在前缀里且每次都不同，缓存命中率会趋近于零。

## 二、注意力：模型的核心算子

### 2.1 从「一句话里每个词该看谁」说起

注意力机制要解决的问题是：句子中每个 token 应当聚合哪些 token 的信息。

给定输入矩阵 $X \in \mathbb{R}^{n \times d}$，模型用三个可学习矩阵投影出查询、键、值：

$$
Q = XW_Q,\quad K = XW_K,\quad V = XW_V
$$

然后计算缩放点积注意力：

$$
\text{Attention}(Q,K,V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}} + M\right)V
$$

其中 $M$ 是因果掩码矩阵（causal mask）：第 $i$ 个位置只能看到 $j \le i$ 的位置。这是自回归模型"不能偷看未来"的实现方式——训练和推理时用同一个掩码，训练效率远高于递归式 RNN。

除以 $\sqrt{d_k}$ 是为了防止点积数值过大导致 softmax 梯度消失：$d_k$ 越大，点积的方差越大。

### 2.2 多头不是「多个人在看」

多头注意力把 $d$ 维拆成 $h$ 组，每组独立做注意力，最后拼接再投影。直觉上不同头会学到不同模式——有的头关注句法依存，有的头关注指代消解，有的头做「上文中的前一个词」这类局部匹配。但这只是相关性，不是机制保证；不同模型、不同层里头的分工差异很大，不要把多头当成可解释性工具来用。

### 2.3 分组查询注意力（GQA）与多查询注意力（MQA）

这是推理阶段最重要的优化之一。标准 MHA 中，每个头都有独立的 K 和 V，KV Cache 大小是：

$$
2 \cdot n \cdot L \cdot h \cdot d_k \cdot \text{bytes}
$$

GQA 让若干个头共享同一组 K/V（例如 8 个头共享 1 组 KV），MQA 更是让所有头共享一组。Llama 3 70B 用 GQA（8 个 KV 头对应 64 个 Query 头），直接砍掉 KV Cache 体积约 87.5%。**KV Cache 从显存里省出来的空间，直接转化为可并发的请求数**，这是长上下文服务的吞吐瓶颈所在。

### 2.4 位置编码：模型怎么知道顺序

注意力本身是置换不变的——打乱输入顺序，输出只是跟着换位置。所以必须显式注入位置信息。

- **正弦位置编码**（原始 Transformer）：用不同频率的正弦/余弦函数生成位置向量，可外推到训练时未见过的长度。
- **RoPE**（Rotary Position Embedding）：如今的主流。它把位置信息以旋转形式作用在 Q 和 K 上，性质是「相对距离只取决于 RoPE 的相对位置差」，因此天然具备相对位置外推能力，是当前主流开源模型（Llama、Qwen、Mistral 等）的默认选择。

RoPE 的外推有内在边界：训练时未见过的距离会导致注意力分布失真。所谓「YaRN」「NTK-aware 插值」「动态 NTK 缩放」等方法，本质都是在**修改 RoPE 的频率基**（拉低高频、保留高频），把分布强行拉回训练时的形状区间。

### 2.5 归一化、残差与前馈网络

每个 Transformer block 通常是：

```text
x = x + Attention(RMSNorm(x))
x = x + FFN(RMSNorm(x))
```

- **RMSNorm** 取代 LayerNorm：省掉均值计算，只做均方根缩放，效果相当但更便宜，已成为现代模型标配。
- **残差连接**保证梯度能直接回传到浅层，是深层模型可训练的前提。
- **FFN**（SwiGLU / GEGLU）是模型参数量的主要来源：通常 `d_ff ≈ 8/3 × d`（SwiGLU 有三个矩阵，比标准 FFN 多一个但需要把隐层压到 2/3）。70B 级模型的参数约 85% 在 FFN 里。

**结论一**：注意力决定「信息怎么流动」，FFN 决定「知识存在哪里」。推理时注意力部分计算随序列长度平方增长，FFN 部分是固定成本。这决定了长上下文场景的优化重点在注意力侧。

## 三、训练：模型如何获得能力

### 3.1 预训练目标

主流模型使用自回归语言建模：最大化 $\sum \log p(x_t \mid x_{<t})$。这个目标简洁到近乎朴素，但它自然包含了大量隐含能力——语法、事实关联、推理模式、代码结构，都以「压缩统计规律」的形式被写进权重里。

关键工程决策是**数据**：同样的架构和算力，数据配比（代码、中文、多语言、书籍、百科、对话的比例）往往比架构微调对最终效果的影响更大。数据清洗（去重、去污染、去低质量网页）同样重要：n-gram 级重复会显著伤害模型，且重复内容在训练中被反复强化。

### 3.2 缩放定律

Kaplan 等人的工作给出了一条经验规律：模型损失随参数量、数据量、算力呈幂律下降，并存在幂律指数约 0.05～0.07 的「不可约损失」部分。

实践含义是明确的：**在固定算力预算下，更大的模型 + 更少的数据，通常优于更小的模型 + 更多的数据**（一旦过了数据重复的临界点）。Chinchilla 修正了这一结论——彼时的大模型普遍「训练不足」，最优数据量应与参数量大致同步增长（约为参数量的 20 倍 token 量级）。后续工作又指出，**推理成本比训练成本更重要**的模型（如 Llama 系列）在同样的训练预算下把更多算力压在推理友好性上，这正是「小而强」路线的胜利。

### 3.3 后训练：把基座变成助手

预训练模型只会续写，不会「回答」。后训练分三层：

1. **SFT（监督微调）**：用高质量「指令—回答」数据继续训练，教会模型遵循指令、套用指定输出格式。这是可用性的分水岭。
2. **偏好对齐**：RLHF（PPO）、DPO、IPO 等方法用人类偏好数据优化「哪种回答更好」。DPO 直接在偏好对上做分类式损失，绕开了显式训练奖励模型，工程复杂度大幅下降。
3. **推理强化（RLVR）**：用可自动验证的奖励（数学答案对错、代码是否通过测试）训练模型思考，这是近年提升数学与代码能力最有效的手段之一。

### 3.4 蒸馏与量化

- **蒸馏**：大模型（教师）生成数据训练小模型（学生），是当前获得「小而强」模型的主流手段。DeepSeek-R1 的关键做法之一就是用 RL 产出的推理轨迹蒸馏给更小的开源模型。
- **量化**：把权重从 FP16 降到 INT8/INT4，或激活值降到 FP8/INT8。权重量化主要影响模型文件与显存占用；KV Cache 量化直接决定长上下文服务的并发能力。

**结论二**：模型能力来自数据与后训练，而生产成本来自推理时的显存带宽。二者需要分开评估。

## 四、推理引擎：生产环境真正的战场

### 4.1 Prefill 与 Decode：两种截然不同的负载

一次推理请求分两个阶段：

- **Prefill（预填充）**：处理整个 prompt，产出第一个 token。计算密集（compute-bound），算力利用率高，可大规模并行。
- **Decode（解码）**：逐个生成 token。每一步都要读一遍全部权重，访存密集（memory-bound），算力利用率低。

这个二分几乎解释了所有推理优化技术的位置：

| 阶段 | 瓶颈 | 主要优化手段 |
| --- | --- | --- |
| Prefill | 算力 | 算子融合、FlashAttention、chunked prefill |
| Decode | 显存带宽 | 量化、投机采样、批处理、KV Cache 管理 |

### 4.2 KV Cache：把注意力变便宜

自回归解码时，第 $t$ 步的注意力需要第 $1..t-1$ 步所有 K、V。把它们缓存下来，第 $t$ 步只需计算新 token 的 Q 与全部缓存 K 的点积——把每步的复杂度从 $O(n^2)$ 降到 $O(n)$。

KV Cache 的代价是显存：70B 模型在 8K 上下文下 KV Cache 可达十几 GB，直接决定并发数。相关技术：

- **PagedAttention**（vLLM 提出）：把 KV Cache 按固定大小的「页」管理，逻辑上连续、物理上离散，避免传统连续分配产生的碎片；再配合 copy-on-write 实现前缀共享。
- **Prefix caching**：跨请求复用相同前缀的 KV，RAG、多轮对话、few-shot 场景收益极大。
- **Chunked prefill**：把长 prompt 切成块，与 decode 阶段交错执行，避免长 prompt 堵死整个 batch（prefill 优先会导致短请求的 TTFT 抖动）。
- **KV Cache 量化**：把缓存从 FP16 降到 INT8/FP8，显存直接减半。

### 4.3 连续批处理：吞吐量的关键

静态批处理要求同一批请求同时开始、同时结束——最长的请求拖着整批。而自回归生成长度差异巨大（有的 10 token，有的 1000 token），静态批的 GPU 利用率极低。

**连续批处理（continuous batching）**在每个解码步动态把新请求插入、已完成的请求移出，使 GPU 始终满载。这项技术通常能带来 2～10 倍吞吐提升，是自建推理服务时投入产出比最高的一步。

### 4.4 投机采样：用小模型换时间

投机采样的思路：用一个便宜的小模型（draft model）快速生成若干候选 token，再用大模型（target model）**一次性并行验证**这些候选；验证通过就全部采纳，否则从分歧点重新生成。

关键性质是**分布无损**：采用严格的接受-拒绝机制后，输出分布与直接用大模型采样完全一致，不是近似。典型收益：

- 小模型足够小、且大模型有大量计算冗余时，2～3 倍加速；
- 批处理场景下收益更大（draft 可以被多个请求共享）；
- 适合输出较长的场景（如代码补全、翻译）。

### 4.5 显存与并发估算

给一个可落地的估算方法。以 70B、FP16、GQA(8 KV 头)、32 层、d=8192、上下文 8K 为例：

- 权重显存 ≈ 70B × 2 bytes ≈ 140 GB（需 2×A100-80G 或 4×48G 卡）
- KV Cache ≈ 2 × n(8192) × L(32) × h_kv(8) × d_head(128) × 2 bytes ≈ 1.07 GB / 请求
- 在 4×48G（192 GB）上留 48 GB 给 KV Cache，理论并发 ≈ 45 条；实际因碎片与临时缓冲打 7 折，约 30 条

**结论三**：并发上限是显存账，不是算力账。**降精度、减上下文、多卡切分**三条路都是在同一张显存表上腾挪。

## 五、采样与解码策略

模型输出的是 logits，需要策略把它变成 token 文本。

- **Temperature**：对 logits 除以 $T$ 后 softmax。$T<1$ 更确定（更保守），$T>1$ 更发散。$T=0$ 等价于贪心解码。
- **Top-k / Top-p**：只在前 k 个或累计概率前 p 的 token 里采样。Top-p（nucleus）通常优于 Top-k，因为它自适应分布形状。
- **重复惩罚**：抑制已出现 token 的概率，缓解复读；但会误伤代码、数学等**必须重复**的场景（变量名、公式），在新模型中通常不必再调。
- **结构化输出（constrained decoding）**：在解码时用有限状态自动机/语法约束 token 集合，保证输出可被 JSON Schema、SQL、正则直接解析。这比「提示模型输出 JSON，然后祈祷它合法」可靠一个数量级。

**工程结论**：生产系统应使用 JSON Schema / grammar 约束解码，而不是靠提示词祈祷；温度一般取 0～0.3（抽取、分类、代码修复），创作类任务才提高。

## 六、长上下文：能力与成本的落差

### 6.1 「支持 128K」不等于「能用好 128K」

长上下文的工程指标和认知指标是两回事：

| 指标 | 含义 | 何时可靠 |
| --- | --- | --- |
| 引擎指标 | 能塞进去、不崩 | 可靠 |
| 检索指标 | 「大海捞针」（Needle in a Haystack） | 中等长度可靠，长上下文仍会退化 |
| 推理指标 | 需要跨多处信息做组合推理 | 显著退化 |

长上下文反而常常**不如**「精检索 + 短上下文」：成本按 token 线性增长，注意力计算按长度平方增长，延迟随之恶化，而推理质量还可能下降。

### 6.2 上下文压缩与外部记忆

生产系统的常见策略：

1. **分层摘要**：把历史对话按时间窗口摘要，只保留最近若干轮原文；
2. **外部记忆**：把事实、笔记、状态写入向量库或 KV 存储，按需检索注入；
3. **子代理隔离**：把大量原始材料（如整份代码库）交给一个上下文很大的子代理处理，只让它返回结论。

这三种做法的共同点：**不让主上下文无限增长**，而是把「记忆」外置。

## 七、评测：如何不靠感觉

### 7.1 指标的层次

- **困惑度（perplexity）**：训练层面的语言建模指标，与下游任务表现相关性有限。
- **任务级准确率**：pass@k（代码）、exact match（问答）、F1（抽取）。需要自建带标注的评测集。
- **综合基准**：MMLU、GSM8K、HumanEval、SWE-bench 等。
- **人类偏好**：Chatbot Arena 的 Elo 类排名，反映主观体验但方差大。

### 7.2 三个必须警惕的问题

1. **数据污染**：基准题目可能已进入训练集，分数虚高。用污染检测工具或使用近发布、少见的私有评测集。
2. **过拟合评测集**：反复在同一个评测集上调提示词，本质是在评测集上过拟合。评测集要隔离，一份用于调优、一份用于终验。
3. **非确定性**：温度、模型版本、提示词微调都会造成波动。单次对比不可靠，要多次采样取分布。

**结论四**：上线前必须有**自建回归评测集**（几十到几百条真实任务 + 期望输出/断言），每次换模型、换提示、换引擎都跑一遍，否则「感觉变好了」不可信。

## 八、常见误区清单

| 误区 | 事实 |
| --- | --- |
| 「模型参数越多越强」 | 决定性因素是数据与后训练；70B 弱模型可能输给 7B 强模型 |
| 「上下文越长越好」 | 成本线性涨、注意力平方涨、推理质量可能降 |
| 「加更多 few-shot 一定提升」 | 超过一定数量后反而干扰，且挤占上下文；示例质量远比数量重要 |
| 「提高温度能解决幻觉」 | 温度只影响采样分布，不改变模型的错误信念；幻觉靠检索、验证、约束解决 |
| 「流式输出更贵」 | 流式不改变 token 数，只改变首字节延迟体验；但会增加连接与调度开销 |
| 「max_tokens 越大越好」 | 上限只是截断阈值；过大的上限会诱导模型「写长」并放大成本 |
| 「本地部署一定更便宜」 | 要算上显存、运维、电费与低利用率；低流量用 API、高并发自建通常更划算 |

## 九、多模态：视觉输入如何进入语言模型

多模态模型并没有推翻上面的链路，只是把「非文本 token」也送进了同一个序列。

### 9.1 视觉编码器与 patch

图像先经视觉编码器（ViT 系列）切成 patch（如 14×14 像素一块），每个 patch 经线性投影变成一个向量，与文本 embedding 一起加入序列。关键的成本事实是：**一张 1024×1024 图片大约产生 1000～1500 个 token**，分辨率直接决定账单。

工程上因此形成两种典型策略：

- 高分辨率整图输入：细节保留好，token 消耗巨大；
- 先用视觉模型生成文字描述，再把描述作为文本上下文交给 LLM：token 便宜，但丢失细节，且多一跳延迟。

折中做法是「按需路由」——先用低成本方案判断图片是否需要高精度解析，只有在识别失败或用户明确要求细节时才升级分辨率。

### 9.2 投影层与模态对齐

视觉向量与文本向量维度不同，需要一个投影层（projector）映射到同一空间并做归一化，这个投影层通常在预训练后期单独训练。工程含义是：**多模态能力主要体现在视觉编码器与投影层，底座语言模型可以复用**，这也是很多「Qwen-VL / LLaVA 系」共享同一语言底座的原因。

### 9.3 音频与视频

音频通常先用 Whisper 类模型转成文本或离散 token 序列（再拼进 LLM 上下文），视频则是「关键帧抽取 + 音频转写」的组合。多模态链路的延迟是**串行累加**的：ASR 5 秒 + VLM 3 秒 + LLM 4 秒 = 12 秒。因此工程重点通常不是加速单点，而是并行化与流式化（先吐 ASR 结果，让 LLM 边收边算）。

## 十、推理服务的可观测性与 SLO

推理服务和普通 Web 服务最大的区别是：**它的延迟由内部循环决定，且失败模式极其多样**。

### 10.1 三个核心指标

| 指标 | 定义 | 意义 |
| --- | --- | --- |
| TTFT | 首 token 延迟 | 由 prefill 主导，用户感知最强 |
| TPOT | 每输出 token 时间 | 决定「阅读速度」，即流式体感 |
| 吞吐 | tokens/s（总） | 决定成本与并发能力 |

TTFT 与 TPOT 必须分开看：一次「慢」的投诉，可能是排队（TTFT 高）、也可能是生成慢（TPOT 高），两者的处置方式完全相反。

### 10.2 必须采集的指标

- 请求级：输入/输出 token 数、TTFT、TPOT、总耗时、是否截断、finish_reason；
- 队列级：排队时长、批大小分布、KV Cache 使用率、抢占次数；
- 模型级：GPU 利用率、显存占用、KV Cache 命中率、prefix cache 命中率；
- 业务级：结构化输出解析失败率、重试率、降级触发次数。

### 10.3 典型故障与定位顺序

**症状一：吞吐随并发上升而下降。** 常见原因是 KV Cache 显存不足触发动态抢占（vLLM 的 preemption），请求被换出换入。先看 KV Cache 使用率与 preemptions 计数，再看是否长请求独占批。

**症状二：TTFT 偶发尖刺。** 通常是长 prompt 的 prefill 阻塞了批内其他请求。对策是启用 chunked prefill，或把长请求与短请求分到不同队列（双模型部署：大模型管长文，小模型管短问答）。

**症状三：输出重复、卡在某个片段。** 通常是模型本身在该任务上退化（不是引擎问题）。验证方法：用相同 prompt 直连 API 复现，若 API 也重复，就是模型/提示词问题；只有自建才重复，才是引擎或量化问题。

**症状四：结构化输出偶发不合法。** 检查是否真正使用了约束解码，还是仅靠提示词要求 JSON。

## 十一、成本与容量规划

### 11.1 一个可复用的估算框架

单请求成本 ≈ (输入 token × 输入单价 + 输出 token × 输出单价)

月度成本 ≈ QPS × 平均输入 × 3600 × 24 × 30 × 单价（自建则换成：显存成本 / 有效利用率）

自建推理的真实成本项：

1. **硬件**：GPU 采购或租赁；
2. **利用率**：业务波峰波谷明显时，低谷的卡是纯亏损——这是自建最大的隐性成本；
3. **运维**：升级、扩缩容、监控、故障处理的人力；
4. **工程**：推理引擎调优、量化验证、兼容性问题。

经验判断：**流量小或波动大 → 用 API；流量大且平稳、延迟要求高、且有专门人力 → 自建**。中间地带可以用「API 兜底 + 自建承接高峰」的混合架构：自建处理稳定的高峰负载，突发溢出回落到 API，兼顾成本与体验。

### 11.2 上下文长度的成本杠杆

一个 5000 token 的输入，在很多 API 上比 1000 token 的输入贵 4～5 倍，而且贵的是**缓存命中的部分也按比例**（多数厂商对输入 token 统一计费，缓存命中只是打折而非免费）。因此：

- 系统提示、历史摘要、参考资料要**分层复用**并开启 prefix caching；
- RAG 检索到的文档要**排序稳定**并截断到必要长度；
- 多轮对话不要每轮重发全部历史，做增量摘要。

这三条能带来的成本下降，通常比「换一个便宜一点的模型」更可观，且不影响质量。

## 十二、小结

把整条链路压缩成六句话：

1. 模型看到的是 token，不是文字；分词方式直接影响成本。
2. 注意力负责信息流动，FFN 负责知识存储；位置信息必须显式注入。
3. 能力来自数据与后训练，成本的约束来自推理时的显存带宽。
4. Prefill 是算力问题，Decode 是带宽问题；所有优化手段都落在这两者之一上。
5. KV Cache 与连续批处理是吞吐量的真正杠杆；量化是把显存表腾挪给并发的方式。
6. 输出质量靠约束解码与评测集保证，不靠提示词运气。

理解了这些，你在面对「换个模型会不会更慢」「要不要自建推理」「上下文能不能开大」这类问题时，就不再需要猜——你可以算。
