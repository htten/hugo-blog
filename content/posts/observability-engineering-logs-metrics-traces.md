## 引言：三类信号，三种认知

线上故障时，工程师真正想回答的是三个不同的问题：

1. **「现在怎么样？」** —— 系统整体的健康状况（CPU、内存、QPS、错误率、延迟分布）。
2. **「哪里出了问题？」** —— 哪台机器、哪个服务、哪个租户的哪个请求出的问题。
3. **「为什么？」** —— 这个请求在内部经历了什么，耗时花在哪一环。

三个问题对应三类信号，它们**不是替代关系，而是互补关系**：

| 信号 | 语义 | 回答的问题 | 数据形态 | 单位成本 |
| --- | --- | --- | --- | --- |
| **指标（Metrics）** | 聚合后的数值 | 现在怎么样 | 时间序列 | 低（高基数是陷阱） |
| **日志（Logs）** | 离散事件记录 | 发生了什么 | 文本行 | 中（量最大） |
| **链路追踪（Traces）** | 单个请求的因果链 | 为什么 | 有嵌套的结构 | 高（采样后可控） |

常见的错误是把三者混为一谈：

- **只上指标**：知道 QPS 掉了，但不知道是哪个下游超时；
- **只上日志**：翻了几十万行日志，最后靠 grep 拼出时间线；
- **只上链路追踪**：单请求看得很清楚，但没法回答"过去一小时的错误率是多少"。

本文按这个顺序展开：先讲三种信号各自的语义边界和成本模型，再讲 OpenTelemetry 的统一数据模型与采样，再讲 eBPF 的能力边界，最后给落地顺序。

全文区分三类陈述：**已确认**（有官方文档或规范直接支撑）、**工程经验**（社区常见做法，随版本与场景变化）、**待验证**（需要你在自己的环境上测）。

## 一、指标：聚合的代价是丢失细节

### 1.1 指标的类型

Prometheus 生态的四类指标：

| 类型 | 语义 | 示例 | 能否加标签 |
| --- | --- | --- | --- |
| **Counter** | 只增不减的累计值 | 请求总数、错误总数 | 可以 |
| **Gauge** | 可增可减的瞬时值 | 队列长度、连接数、内存占用 | 可以 |
| **Histogram** | 分桶计数的分布 | 请求延迟 | 可以（桶有基数成本） |
| **Summary** | 分位数（客户端算） | 请求延迟 P99 | 可以（不可跨实例聚合） |

**Histogram 与 Summary 的关键区别**：

- **Histogram** 在服务端按预设桶计数，**可以跨实例聚合**——把 10 个实例的桶计数相加，得到全局分布。代价是桶边界要事先定好，且精度受限于桶宽。
- **Summary** 在客户端算分位数，**无法跨实例聚合**——各实例的 P99 不可加。而且 Summary 的分位数是流式算法，样本顺序影响结果。

**结论：需要全局分位数就用 Histogram + `histogram_quantile()`，不要用 Summary。**

### 1.2 基数爆炸：最常见的生产事故

**基数（cardinality）**是指标的时间序列数量。它等于所有标签值的笛卡尔积：

```
时间序列数 = 服务数 × 实例数 × 状态码数 × 方法数 × ...
```

危险的不是"指标多"，而是**某个标签的值不可控**。典型事故模式：

```go
// ❌ 把用户 ID 放进标签
metrics.RequestDuration.WithLabelValues(userID, endpoint).Observe(d)

// ❌ 把原始 URL（含 ID）放进标签
metrics.RequestDuration.WithLabelValues(r.URL.Path).Observe(d)

// ✅ 只用有限枚举值
metrics.RequestDuration.WithLabelValues(method, statusClass, route).Observe(d)
```

后果是连锁的：

1. Prometheus 内存暴涨（每个序列都要存 chunk、label 元数据）；
2. 查询变慢甚至超时；
3. **采集失败反过来打挂了业务进程**——这是最严重的情形，因为可观测性组件把应用搞挂了。

**判断标准：一个标签的值集合是否可枚举、是否有限。** `user_id`、`request_id`、`full_path`、`error_message` 都不合格。

**动态路由的解法**：用**路由模板**而不是实际路径。`/users/12345` → `/users/{id}`。框架层通常能拿到路由模板（Express 的 `req.route.path`、FastAPI 的 `request.scope["route"].path`、Spring 的 `HandlerMapping`）。

### 1.3 指标的四个黄金信号（USE / RED）

Google SRE 书籍提出的四个黄金信号（The Four Golden Signals）：

| 信号 | 含义 | 面向 |
| --- | --- | --- |
| **延迟（Latency）** | 请求耗时分布 | 用户体验 |
| **流量（Traffic）** | QPS / 并发数 | 容量规划 |
| **错误（Errors）** | 失败请求比例 | 质量 |
| **饱和度（Saturation）** | 最受限资源的使用率 | 余量 |

Brendan Gregg 的 **USE 方法**是资源维度的版本：

| 指标 | 含义 | 怎么查 |
| --- | --- | --- |
| **Utilization** | 资源实际工作时间占比 | CPU 使用率、磁盘 IO 利用率 |
| **Saturation** | 必须排队才能完成工作的程度 | 队列长度、等待时间 |
| **Errors** | 失败的次数 | 错误率、超时数 |

**USE 与黄金信号的关系**：黄金信号是**面向服务**的（外部视角），USE 是**面向资源**的（内部视角）。两者互补：用户抱怨慢，可能是饱和度（磁盘 IO 打满），也可能是依赖方慢；只有把两个视角合起来才能定位。

### 1.4 分位数不是平均值

一个常被纠正的误解：**平均延迟不能替代分位数。** 典型的延迟分布是长尾的：

```
延迟分布（1000 个请求）
  990 个: 10-50ms
    9 个: 100-500ms
    1 个: 5000ms   ← 平均值被拉高，但 99% 的用户体验很好
```

如果只看平均值（假设 55ms），你无法发现那 1% 的 5 秒请求——而那可能正是超时的来源。**SLO 通常定义在分位数上**（如"99% 的请求延迟 < 300ms"）。

### 1.5 指标的成本模型

指标存储成本近似为：

```
存储量 ≈ 时间序列数 × 采样间隔数 × 每点字节数
```

以 Prometheus 为例，每个样本除了值还有 timestamp、label name/value、一小段 chunk 元数据，实际每样本开销在 1-3 字节量级（压缩后）。但**时间序列数**才是主导因素——10 万序列 × 15 秒一个点 × 30 天 retention 就相当可观。

**降低成本的四个杠杆**：

1. **减少基数**（最重要）：去掉无界标签；
2. **提高直方图桶的粒度**（减少桶数）；
3. **加长 scrape interval**（15s → 30s → 60s，代价是丢失短时尖峰）；
4. **分环境分实例存储**，而不是全塞进一个 Prometheus。

## 二、日志：事件的离散记录

### 2.1 结构化日志优先

**结构化日志**（每条日志是一个 JSON 对象）比纯文本日志在检索层面有数量级优势：

```json
{
  "timestamp": "2026-11-27T10:23:45.123Z",
  "level": "error",
  "service": "checkout",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "user_id": "u_8f3a2",
  "order_id": "ord_20261127_00123",
  "msg": "payment gateway timeout",
  "duration_ms": 5003,
  "error": {"type": "TimeoutError", "stack": "..."}
}
```

纯文本日志需要正则解析才能提取字段，结构化日志直接过滤：

```bash
# 找出所有支付超时的错误日志
jq 'select(.msg | test("timeout"))' access-*.jsonl

# 按 order_id 聚合
jq -r 'select(.order_id) | .order_id' access-*.jsonl | sort | uniq -c | sort -rn
```

**注意 `trace_id` 的存在**——它是日志与链路追踪的连接点。日志告诉你"发生了什么"，trace 告诉你"它属于哪个请求的哪一段"。

### 2.2 日志级别与成本

| 级别 | 语义 | 生产环境 | 成本影响 |
| --- | --- | --- | --- |
| TRACE | 逐细节追踪 | 关闭 | 极高 |
| DEBUG | 调试信息 | 通常关闭 | 高 |
| INFO | 正常业务事件 | 开启 | 中 |
| WARN | 异常但可恢复 | 开启 | 中 |
| ERROR | 失败需要人看 | 开启 | 中（但可能洪水） |

**生产环境关掉 DEBUG/TRACE 是省钱的第一招**，也是防止日志淹没告警信号的第一招。

**日志洪水（log flooding）** 是常见事故：某个错误分支在故障期间每秒打 10 万行，把日志管道打满，反而把关键日志挤掉了。防御手段：

- **采样**：同类错误在时间窗口内只打前 N 次，之后聚合（"此错误再发生 1,000,000 次"）；
- **限流**：按 key 限流；
- **分级降噪**：故障时自动调高日志级别。

### 2.3 采样与保留策略

日志的三级过滤：

1. **采集端过滤**：应用侧不产生无用日志（成本最低，效果最好）；
2. **管道端采样**：按规则采样（如只保留 error 和采样 10% 的 info）；
3. **存储端保留**：按时间/容量淘汰（如热存 7 天，冷存 90 天）。

**排障时的痛点**：排障需要的信息被采样掉了。业界的一个折中是**"tail-based sampling"（基于结果的采样）**：先全部采集到内存缓冲，攒一个窗口后再决定丢哪些。

- 采样器在窗口结束时看结果：**有错误的请求全留，成功的请求按比例留**。

这比头部采样（head-based，在入口就按比例丢）更合理——但代价是要缓存整个窗口的 trace。

### 2.4 关联 ID 的传播

日志串联的关键是 **correlation ID** 的正确传播。跨越进程边界时，ID 必须跟着请求走：

- **同步调用**：HTTP 头（`X-Request-Id`、`traceparent`）；
- **异步调用**：消息体或消息头（Kafka header、SQS message attribute）；
- **跨进程/跨机**：eBPF 可以从内核层面注入，避免改代码。

**异步场景最常出问题**：消费者日志里的 `trace_id` 为空，说明 ID 传播链路断了。检查消息生产端是否把 ID 写进了消息头，而不是只放在 HTTP 头里。

## 三、链路追踪：因果链的结构化表达

### 3.1 Trace 与 Span

**Trace** 是一次请求的完整因果链，**Span** 是其中的一段操作。

Span 的关键属性：

| 属性 | 语义 |
| --- | --- |
| `trace_id` | 整个请求的全局 ID |
| `span_id` | 当前操作的 ID |
| `parent_span_id` | 父操作 |
| `name` | 操作名（低基数，如 `GET /users/{id}`） |
| `kind` | `SERVER` / `CLIENT` / `PRODUCER` / `CONSUMER` / `INTERNAL` |
| `start_time` / `end_time` | 时间区间 |
| `status` | `ERROR` / `OK` / `UNSET` |
| `attributes` | 键值对 |

Span 之间通过父子关系形成树，跨进程通过 `parent_span_id` 关联。**这棵树就是"为什么慢"的答案**：耗时 5 秒的请求，慢在哪个子 span 上，一目了然。

### 3.2 W3C Trace Context 与分布式上下文传播

现代标准是 **W3C Trace Context**，用两个 HTTP 头传播：

```http
traceparent: 00-<32-hex-trace-id>-<16-hex-parent-span-id>-01
tracestate: vendor1=...,vendor2=...
```

`traceparent` 的结构：`版本(2 hex) - trace-id(32 hex) - parent-id(16 hex) - flags(2 hex)`。

老系统用的是 B3 头（`X-B3-TraceId` 等），现在多采用**双写**过渡：同时发 `traceparent` 和 B3 头，接收端任一可用即可。

### 3.3 采样策略：这是最需要决策的一环

追踪数据量大，**必须采样**。采样策略的选择直接决定你能看到什么。

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **头部采样（head-based）** | 在入口按比例决定 | 实现简单，无额外成本 | 采样决策是盲的，可能把唯一的故障请求丢掉 |
| **尾部采样（tail-based）** | 缓冲后按结果决定 | 错误请求必定保留 | 需要缓冲，延迟成本高 |
| **概率采样** | 按固定概率 | 统计意义清晰 | 同上，盲采 |
| **规则采样** | 按业务规则 | 精确控制 | 规则维护成本高 |

**尾部采样的规则设计**是这类系统最有价值的部分：

```
保留规则：
- 状态码 >= 500 → 全部保留
- 耗时 > 2s → 全部保留
- 包含特定业务错误码 → 全部保留
- 其余 → 按 5% 概率保留
```

这样「5% 的成功流量」提供正常基线，「100% 的错误和慢请求」提供排障证据。这比 100% 采样然后事后过滤要省钱得多，也比盲目头部采样要有效得多。

### 3.4 OpenTelemetry 的数据模型

OpenTelemetry（OTel）是 CNCF 的可观测性框架，核心价值是**统一了三大信号的采集**：同一个 SDK 同时产出 metrics、logs、traces。

关键概念：

| 概念 | 说明 |
| --- | --- |
| **Signal** | metrics / logs / traces 三种信号 |
| **Resource** | 产生数据的实体（服务、实例、主机） |
| **Instrument** | 具体的度量（Counter、Histogram、Span、LogRecord） |
| **Scope** | 产生数据的库/包（instrumentation scope） |
| **Pipeline** | 采集 → 处理 → 导出的链路 |
| **Collector** | 独立运行的采集代理 |
| **Exporter** | 把数据送到后端（OTLP、Prometheus、Jaeger…） |
| **Processor** | 批处理、过滤、脱敏、采样 |

**Collector 的架构**（数据流向）：

```
应用 SDK  ──OTLP/gRPC──▶  Collector  ──▶  Processor  ──▶  Exporter  ──▶ 后端
                            │
                            ├── 采样 Processor
                            ├── 脱敏 Processor（去掉敏感字段）
                            ├── 批处理 Processor（batch）
                            └── 资源属性 Processor（补 host、k8s pod 信息）
```

**Collector 的价值**在于把「应用里的 SDK」和「数据去哪」解耦：应用只管按 OTel API 打点，不关心后端是 Jaeger 还是 Tempo；采集端、采样策略、后端切换都不需要改应用代码。

**语义约定（Semantic Conventions）**定义了标准属性名——`http.request.method`、`service.name`、`k8s.pod.name` 等。遵循约定意味着你的数据可以被现成的看板和查询直接使用，不用为每个团队自定义字段名。

### 3.5 采样决策在何处做出

采样决策必须在**上下文传播之前**做出，且所有参与方要一致：

- 入口服务决定是否采样 → 通过 `traceparent` 的 flags 字段传播；
- 后续服务读取 flags，不自己重新决定；
- **下游不能"复活"一个未采样的 trace**（否则会产生孤立的子 span，没有父节点）。

W3C Trace Context 的 flags 位：

```
flags = 00  → 不采样
flags = 01  → 采样
```

这是 OpenTelemetry 的 `TraceFlags`。采样决策的一致性是分布式追踪正确性的前提——**如果每个服务独立决定采样，你会看到大量"断头"的 span 片段**。

### 3.6 采样的成本

粗略估算：一个 span 约 1-3KB（JSON 编码后），一个请求平均 10 个 span → 30KB/请求。

```
QPS 1000 × 采样率 5% = 50 traces/s × 30KB = 1.5 MB/s ≈ 129 GB/天
```

这就是为什么必须采样，而且必须**自动降采样**。很多系统在流量高峰时自动降低采样率，这会带来一个副作用：**高峰期的问题更难排查**。所以降采样策略要保守，并在指标上暴露当前采样率。

## 四、eBPF：内核层的观测能力

### 4.1 eBPF 是什么

eBPF 是 Linux 内核里的可编程执行环境：把一段经过验证的 C 程序（或其他语言编译成的字节码）加载进内核，在特定钩子点执行。

验证器（verifier）保证程序**不会破坏内核**：检查寄存器状态、控制流、内存访问边界。这让非特权用户也能安全地挂载探针。

官方内核文档把 eBPF 描述为 "a technology for running programs in a privileged context ... in a controlled and safe manner"。

### 4.2 eBPF 在可观测性中的定位

eBPF 提供的独特能力是**零侵入观测**：

| 能力 | 说明 | 传统方式 |
| --- | --- | --- |
| 系统调用级指标 | 每个 syscall 的次数与延迟 | 需要 instrument 代码 |
| 网络流量元数据 | 每连接的状态、延迟、重传 | 需要抓包（开销大） |
| 进程/线程行为 | 调度延迟、off-CPU 时间 | 需要 profiler 集成 |
| 内核函数追踪 | 内核内部路径 | 需要内核版本特定的 patch |
| 网络流（flow）记录 | L4 连接级别的连接与字节数 | netflow/sFlow 采样 |

**关键优势：不需要改应用代码，也不需要重启。** 对于无法改造的第三方组件、老旧系统、内核模块，这是唯一可行的观测手段。

### 4.3 主要 eBPF 可观测性工具

| 工具 | 能力 | 备注 |
| --- | --- | --- |
| **bpftrace** | 写几行脚本即时追踪 | 适合探索和一次性诊断 |
| **Pixie** | 自动生成服务拓扑与 RED 指标 | 需 sidecar 或 agent |
| **DeepFlow** | eBPF 全链路可观测 | 开源，Cilium 生态 |
| **Cilium/Hubble** | L7 网络可观测 | K8s 网络场景 |
| **Parca** | 持续性能剖析 | 火焰图，可下钻到函数级 |
| ** Inspektor Gadget** | 多种 gadget 集合 | 调试与生产兼顾 |

### 4.4 eBPF 的边界与代价

**必须说清楚的限制**：

1. **内核版本依赖**：BPF CO-RE（Compile Once – Run Everywhere）技术让探针能跨内核版本工作，但**并非所有特性都跨版本可用**。需要内核 5.x+ 才有完整能力，某些工具要求 5.8+ 或 5.15+。
2. **开销不为零**：探针在每个命中的路径上执行，即使逻辑很轻，累计开销也随事件频率线性增长。高频 syscall（如 `read`/`write`）上挂全量探针可能带来个位数百分比的性能影响。
3. **需要特权**：加载 BPF 程序通常需要 `CAP_BPF` + `CAP_PERFMON`（或 root）。容器里需要额外的 capabilities 配置。
4. **数据量可能爆炸**：系统调用级别的追踪，每秒可能产生百万级事件。生产环境必须做过滤和聚合，不能全量导出。
5. **不能替代应用层追踪**：eBPF 看到的是「进程 A 调用了 connect 到某个 IP」，但不知道那是不是一次 HTTP 请求、也不知道业务语义。它擅长**发现未知问题**和**无侵入基线**，不擅长**业务语义查询**。
6. **哈希五元组不等于服务语义**：NAT、Service Mesh 代理、连接复用都会让「IP:端口 → 服务」的映射失真。

### 4.5 eBPF 与传统监控的分工

务实的分工是：

| 问题 | 首选工具 |
| --- | --- |
| "这个服务现在多少 QPS？" | 应用指标（Prometheus） |
| "这个错误请求经过了哪些服务？" | 链路追踪（OTel） |
| "日志里这条记录到底对应哪个请求？" | 日志 + trace_id |
| "这个进程为什么 off-CPU？" | eBPF 性能剖析（Parca） |
| "这个 TCP 连接为什么这么慢？" | eBPF 网络观测 |
| "这个未知的内存增长来自哪个库？" | eBPF（无侵入发现） |
| "系统调用层面有什么异常行为？" | eBPF / bpftrace |

**eBPF 的独特价值在最后三行**：这些是应用层观测手段覆盖不到的地方。

## 五、落地顺序与工程实践

### 5.1 从零开始的正确顺序

可观测性体系的建设顺序有明确的依赖关系：

**第一步：指标（基础设施 + 应用 RED）**

- 基础设施：CPU、内存、磁盘、网络、连接数；
- 应用：请求数、错误率、延迟分位数；
- **先做指标，因为它成本最低、发现问题最快。**

**第二步：结构化日志**

- 统一 JSON 格式、必备字段（timestamp / level / service / trace_id / msg）；
- 建立日志保留策略和采样；
- **先做日志，因为它是排障时唯一能看到"细节"的地方。**

**第三步：链路追踪**

- 引入 OTel SDK；
- 关键路径自动埋点（框架集成）；
- 传播上下文（HTTP + 消息队列）；
- 配置采样策略；
- **最后做追踪，因为它成本最高，且需要前两步的基础设施。**

**第四步：eBPF / 深度观测（按需）**

- 在上面的体系已经能覆盖常规排障后再引入；
- 从单个明确的问题场景切入（如"服务间延迟异常"），不要一上来就全量部署。

**反模式**：先上 eBPF 全链路追踪，再补基础指标——你会得到一堆看不懂的数据，却没有回答"服务健康吗"的能力。

### 5.2 告警设计：只对"需要人做事"的情况告警

告警泛滥是可观测性体系失败的最常见方式。设计原则：

**原则一：告警必须可执行。** 每条告警都应该能回答"收到后我做什么"。答不出来就不要告警。

**原则二：用 SLO 烧毁率告警，而不是用资源阈值告警。**

```
烧毁率 = (错误率 - SLO 阈值) / (1 - SLO 阈值)
```

Google SRE 推荐的告警条件：

| 窗口 | 短窗口 | 长窗口 | 烧毁率 |
| --- | --- | --- | --- |
| 1 小时 | 5 分钟 | 1 小时 | 14.4× |
| 6 小时 | 30 分钟 | 6 小时 | 6× |
| 3 天 | 6 小时 | 3 天 | 1× |

含义：**在长窗口（1 小时）烧掉 14.4 倍预算时告警，说明按这个速度 5 分钟就会耗尽全月预算。**

**原则三：分级。**

| 级别 | 含义 | 通知方式 |
| --- | --- | --- |
| P1 紧急 | 用户不可用 | 电话 / 立即 |
| P2 高 | 降级但可用 | 即时消息 |
| P3 中 | 有风险但未影响用户 | 工单 / 次日汇总 |

**原则四：用分位数而非均值。** 告警阈值应设在"影响用户"的位置，而不是"技术上偏高"的位置。

**原则五：告警必须有 runbook 链接。** 没有 runbook 的告警只会消耗值班人的耐心。

### 5.3 高基数问题的自检

上线前问三个问题：

1. 这个标签的值集合是**有限可枚举**的吗？
2. 如果不是，我能接受它带来的序列数增长吗？
3. 这个指标是**在进程内聚合**还是**在标签里区分**？（前者永远更安全）

**危险指标清单**：`user_id`、`email`、`request_id`、`session_id`、完整 URL、错误消息全文、文件路径（动态部分）。

### 5.4 上下文丢失的排查

日志或 span 里 `trace_id` 为空，问题在传播链路。排查顺序：

```
1. 入口服务是否创建了 trace？（客户端请求是否带了 traceparent）
2. 同步调用是否透传了 HTTP 头？（检查中间代理/网关是否剥离）
3. 异步调用是否把 ID 写进了消息头？（不只是 body）
4. 消费端是否从消息头读取？（不是从 body）
5. 是否有 SDK 版本过旧不支持 W3C 格式？
```

**中间层剥离头是常见原因**——某些反向代理或 API 网关默认只透传白名单头。

### 5.5 一次故障排查的完整路径

一个典型的排查流程，展示三类信号如何配合：

```
告警触发：错误率 2.1% > 1%（SLO 烧毁率告警）
    ↓
看指标：哪个服务的错误率涨？→ checkout-service（1.8%），payment-service 正常
    ↓
看日志：grep trace_id / 抽取该服务的 error 日志
    ↓
日志发现：msg="payment gateway timeout", duration_ms=5003
    ↓
但这个请求的 trace 在哪？→ 从日志里的 trace_id 反查 trace
    ↓
看链路：trace 显示 checkout → payment 调用耗时 5s，
        其中 DNS 解析占 4.8s  ← 根因定位
    ↓
处置：DNS 解析到内网地址绕行 / 换一个 DNS
    ↓
事后：加一个"下游调用 DNS 耗时"的指标 + 告警阈值
```

注意最后一步：**故障恢复后要把这次排障过程中缺失的观测能力补上**，这是可观测性体系持续演进的方式。

### 5.6 工程清单

| 检查项 | 判定 | 说明 |
| --- | --- | --- |
| 所有标签值有限可枚举 | 逐个标签审查 | 防基数爆炸 |
| 路由标签用模板不用实际路径 | 检查埋点代码 | 防基数爆炸 |
| 日志为结构化 JSON | 看日志样本 | 可检索 |
| 日志含 `trace_id` | 看日志样本 | 可与 trace 关联 |
| 生产关闭 DEBUG/TRACE | 看配置 | 成本控制 |
| 有日志采样/限流 | 看采集配置 | 防日志洪水 |
| 上下文跨消息队列传播 | 检查生产/消费代码 | 防 trace 断裂 |
| 采样决策入口统一 | 检查采样配置 | 防孤立 span |
| 错误/慢请求全量采样 | 看采样规则 | 保证可排障 |
| 告警基于烧毁率 | 看告警规则 | 面向 SLO |
| 每条告警有 runbook | 点开告警条目 | 可执行 |
| 每条告警有责任人 | 看路由配置 | 有人处理 |
| OTel 用语义约定属性名 | 检查属性名 | 可复用看板 |
| 敏感字段在 Collector 脱敏 | 看 processor 配置 | 合规 |
| 敏感信息不用 ARG/日志明文 | 代码审查 | 防泄露 |

## 小结

1. **三种信号回答三个不同的问题**："现在怎么样"用指标，"哪里出了问题"用日志+追踪，"为什么"用追踪。互相不可替代。
2. **指标的成本由基数主导**。把 `user_id`、实际 URL 放进标签是最常见的生产事故——可观测性组件把业务打挂。标签值必须有限可枚举。
3. **Histogram 能跨实例聚合，Summary 不能**。需要全局分位数就用 Histogram。
4. **日志的核心是结构化和关联 ID**。JSON 格式 + `trace_id` 是检索和串联的基础；生产关掉 DEBUG/TRACE 是省钱和防洪水第一招。
5. **追踪的采样策略是核心决策**。尾部采样（错误和慢请求全留 + 成功流量按比例留）比头部采样有效得多；采样决策必须在入口统一做出。
6. **OpenTelemetry 的价值在于统一三大信号**，Collector 把"应用埋点"和"数据去哪"解耦，语义约定让数据可复用。
7. **eBPF 提供零侵入的内核层观测**，独有价值在"发现未知问题"和"无侵入基线"，但它不能替代应用层追踪，也受内核版本、权限、开销限制。
8. **建设顺序：指标 → 日志 → 追踪 → eBPF**。反过来做会得到一堆看不懂的数据。
9. **告警基于 SLO 烧毁率**，每条告警必须可执行、有 runbook、有责任人。告警泛滥是可观测性体系失败的头号原因。
