## 引言：为什么 RAG 容易演示、难以生产

过去一年，几乎所有大模型应用都多多少少带一点 RAG（Retrieval-Augmented Generation，检索增强生成）：给模型挂一个知识库，让它回答时不只依赖训练时记住的知识，还能查文档、查工单、查产品手册。

Demo 阶段的 RAG 通常只有三步：

```text
文档 → 切段 → 存进向量库 → 用户提问 → 召回 top-k → 拼进 prompt → 模型回答
```

这套流程五分钟就能跑通，但一进生产就会暴露一堆问题：

- 为什么用户问「错误码 4029 怎么处理」，召回的却是讲「错误码 402」的段落？
- 为什么换了 embedding 模型之后，召回率变化比调 prompt 大得多？
- 为什么纯向量检索单独用效果一般，加上 BM25 和重排才稳定？
- 为什么每次优化都感觉「好像好了一点」，但说不清到底好了多少？
- 为什么文档更新之后，旧答案还在持续出现？

这些问题的答案都不在模型侧，而在检索管道里。**RAG 的上限由检索决定，下限由生成决定**：检索把正确证据找回来，模型只是把它组织成答案；检索漏了，再强的模型也只能编。

本文按数据流把 RAG 拆成十个部分：离线索引、文档切分、Embedding、向量检索、混合检索、重排序、评估、失败排查、进阶架构、生产化清单。每个部分只讲工程取舍和失败模式，不讲概念铺陈。

## 一、先把管道拆清楚

### 1.1 离线链路：从文档到可检索的向量

RAG 的数据流可以分成离线（索引）和在线（查询）两条链路。

```text
离线：
原始文档（PDF/Word/HTML/Markdown/工单）
  → 解析（提取纯文本与结构）
  → 切分（chunk）
  → 元数据标注（标题、来源、时间、权限）
  → Embedding（向量）
  → 写入向量库（索引构建）

在线：
用户问题
  → 查询改写 / 意图识别
  → 混合检索（向量 + BM25）
  → 重排序（rerank）
  → 组装 prompt（证据 + 指令 + 约束）
  → 模型生成
  → 引用与可追溯
```

两条链路的更新频率完全不同：离线索引可能是每天/每小时批量跑一次，在线查询要求毫秒级响应。**把这两条链路混在一份代码里，是最常见的架构错误**——索引侧追求吞吐和一致性，查询侧追求延迟和稳定性，优化手段互相冲突。

### 1.2 一个最小可运行的实现

下面是一个刻意简化但结构完整的 Python 伪代码，用来固定后面讨论的术语：

```python
# 离线：构建索引
def build_index(docs):
    chunks = []
    for doc in docs:
        for chunk in split_document(doc):          # 切分
            chunk.metadata = doc.metadata           # 继承来源、权限
            chunks.append(chunk)
    vectors = embed([c.text for c in chunks])       # 批量嵌入
    vector_store.upsert(vectors, chunks)            # 写入向量库
    bm25_index.add(chunks)                          # 写入倒排索引
    return chunks

# 在线：查询
def answer(question):
    query = rewrite_query(question)                 # 查询改写
    vec_hits = vector_store.search(embed(query), k=50)   # 向量召回
    kw_hits = bm25_index.search(query, k=50)             # 关键词召回
    merged = reciprocal_rank_fusion(vec_hits, kw_hits)   # 融合
    reranked = reranker.score(query, merged[:20])        # 精排
    context = assemble(reranked[:5])                # 组装证据
    return llm.generate(query, context)             # 生成
```

这个实现里每个函数都对应后文的一节。工程上的大部分工作，就是把这些函数从「能跑」做到「可测量、可回归、可维护」。

### 1.3 先定指标，再谈优化

在动手优化之前，先回答三个问题：

1. **检索质量怎么衡量**：Recall@K、MRR、NDCG@K（见第七节）。
2. **端到端质量怎么衡量**：忠实度、相关性、引用正确性。
3. **性能预算是多少**：P95 延迟、单次查询成本、索引更新延迟。

没有这三个数字，任何「优化」都是主观感受。RAG 工程的第一步不是调模型，是**建评测集和监控**。

## 二、文档切分：被低估的第一步

切分（chunking）是 RAG 里最容易被敷衍、也最容易影响效果的环节。它决定了检索的最小单位，也决定了模型能看到的上下文粒度。

### 2.1 固定长度切分的问题

最朴素的实现是按固定 token 数切：

```text
每 512 token 一段，重叠 50 token
```

这种切法的问题是：**文档的结构被完全打断了**。一段话可能从中间断开，表格的表头留在上一段，代码块被切成两半，一个完整的论证被拆到两个 chunk 里。检索到其中一半时，模型看到的是残缺信息。

### 2.2 按结构切分

更合理的做法是先解析文档结构，再按语义单元切分：

| 文档类型 | 推荐切分单位 | 注意点 |
| --- | --- | --- |
| Markdown / 技术文档 | 按标题层级（H1/H2/H3） | 保留父标题作为上下文 |
| 网页 / HTML | 按语义标签（section/article） | 去掉导航、页脚、广告 |
| PDF | 按页 + 段落 | 注意双栏排版导致的错序 |
| 工单 / 对话 | 按问题-回答对 | 保留时间、状态、处理人 |
| 表格 | 整表或按行 | 表头必须重复到每段 |
| 代码 | 按函数 / 类 | 保留文件路径与签名 |

**关键原则：切分单位应该是一个「能独立回答问题」的语义单元**。如果一段文字必须依赖上一段才能理解，它就应该和上一段在一起。

### 2.3 重叠窗口：必要的冗余

相邻 chunk 之间保留一定重叠（通常 10%～20%），可以缓解边界切断问题。但重叠不是越多越好：

- 重叠太少：边界信息丢失；
- 重叠太多：索引体积膨胀、重复内容干扰排序、成本上升。

经验做法是：**重叠窗口设为 chunk 大小的 10%～15%，并且只在同一语义单元内重叠，不要跨单元重叠**。

### 2.4 粒度权衡

| chunk 大小 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 小（128～256 token） | 检索精确、上下文干净 | 语义不完整、需要多段拼接 | 事实型问答、FAQ |
| 中（512～1024 token） | 平衡 | 仍可能切断语义 | 通用文档 |
| 大（2048+ token） | 语义完整 | 检索噪声大、挤占 prompt | 长文档综述、法律/合同 |

没有「最优大小」，只有「最适合你文档和问题的粒度」。**正确做法是用评测集扫一遍不同粒度，而不是照抄别人的参数。**

### 2.5 父子切分：小索引、大上下文

一种被广泛使用的折中是 **small-to-big（父子切分）**：

```text
检索用小块（精确命中） → 命中后返回它的父块（完整上下文）
```

例如按句子切分用于检索，但每个句子记录它所属的段落，检索命中句子后把整段交给模型。这样既保留了检索精度，又给模型足够的上下文。代价是索引结构更复杂，需要维护父子映射。

### 2.6 表格、代码、图片的处理

- **表格**：转成 Markdown 表格或「字段：值」的文本，表头重复进每个 chunk。
- **代码**：不要和正文混在一起切；保留文件路径、语言、函数签名。
- **图片**：如果有信息量，用 OCR 或视觉模型生成描述文本再索引；纯装饰图直接忽略。
- **公式**：转成 LaTeX 文本，不要变成图片。

## 三、Embedding：选模型就是选偏见

### 3.1 语义空间与维度

Embedding 模型把文本映射到高维向量，语义相近的文本在向量空间里距离更近。向量维度越高，表达能力越强，但索引体积和检索延迟也越高。常见的维度范围是 384～3072，**维度不是越高越好，要和你的语料、评测结果一起看**。

### 3.2 查询与文档的非对称性

一个重要但常被忽略的事实：**查询和文档是两种不同的文本形态**。查询通常短、口语化、包含疑问词；文档通常长、书面化、结构完整。把查询和文档放在同一个向量空间里比较，天然存在分布差异。

业界的做法分两类：

- **对称检索**：查询和文档用同一种嵌入方式（简单，适合短文档）。
- **非对称检索**：查询和文档用不同的嵌入策略，或者引入查询改写把查询变成长文本（效果更好，适合知识库问答）。

工程上的常见做法是先对查询做**改写/扩展**，再嵌入：把口语化问题改写成陈述句，或者生成多个候选查询（multi-query），分别检索后合并结果。

### 3.3 中文场景的模型选择

中文场景的特殊性在于：分词边界、成语/缩写、专业术语、中英混排。选择模型时不要看榜单排名，要看**你的语料**：

- 用你自己的 50～200 条真实问题做评测；
- 对比不同模型在 Recall@K 上的表现；
- 关注专业术语、同义词、错别字的召回情况。

模型会更新，榜单会过时，**只有自建评测集能告诉你哪个模型适合你**。

### 3.4 批量嵌入、增量更新与版本管理

索引构建时要注意三件事：

1. **批量嵌入**：逐条调用 API 或模型推理极慢，务必批量处理（batch size 根据显存/配额调整）。
2. **增量更新**：文档变更时只重新嵌入受影响的 chunk，不要全量重建。
3. **版本管理**：embedding 模型一旦更换，整个索引必须重建，旧向量和新向量不能混用。给索引记录模型版本号，查询和索引版本不一致时直接拒绝服务。

```python
# 伪代码：带版本校验的嵌入
def embed_chunks(chunks, model_version):
    if index.model_version != model_version:
        raise IndexVersionMismatch(index.model_version, model_version)
    return embedding_model.encode([c.text for c in chunks])
```

## 四、向量检索：ANN 与索引结构

### 4.1 精确检索 vs 近似检索

暴力检索（exact search）计算查询向量与所有文档向量的距离，结果精确但复杂度是 $O(n \cdot d)$。当文档量到百万、千万级时，暴力检索不可用。

近似最近邻（ANN，Approximate Nearest Neighbor）用索引结构换取速度，代价是可能漏掉少量真正最近的向量：

| 方法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 暴力检索 | 全量计算 | 精确 | 慢、内存大 |
| HNSW | 分层可导航小世界图 | 召回高、延迟低 | 内存占用大 |
| IVF | 聚类后只搜部分簇 | 内存友好 | 需要训练、参数敏感 |
| PQ | 乘积量化压缩向量 | 省内存 | 精度损失 |

**工程结论：百万级以下优先考虑 HNSW；内存紧张或十亿级再考虑 IVF + PQ。** 大多数企业知识库都在 HNSW 的适用范围内。

### 4.2 HNSW 的关键参数

HNSW（Hierarchical Navigable Small World）有三个影响最大的参数：

| 参数 | 含义 | 调大效果 | 代价 |
| --- | --- | --- | --- |
| `M` | 每个节点的邻居数 | 召回率上升 | 内存、构建时间上升 |
| `efConstruction` | 构建时的搜索宽度 | 索引质量上升 | 构建时间上升 |
| `efSearch` | 查询时的搜索宽度 | 召回率上升 | 查询延迟上升 |

经验起点：`M=16`、`efConstruction=200`、`efSearch=64`，然后**用评测集扫参数**，不要照搬。查询侧的 `efSearch` 是唯一需要在运行时权衡的参数：延迟敏感就调小，召回敏感就调大。

### 4.3 过滤、分片与多租户

真实系统很少只有向量检索，通常还要带条件过滤（按部门、时间、文档类型、权限）。

- **预过滤**：在 ANN 搜索时同时应用过滤条件。注意过滤比例过高时，HNSW 可能召回不足，需要回退到暴力检索。
- **后过滤**：先搜再过滤，简单但可能过滤后结果不足 K 个。
- **分片**：按租户/部门分索引，查询时路由到对应分片，避免跨租户数据泄漏。

**多租户场景必须把权限过滤放在检索层，而不是生成层**——生成层过滤只能防止模型说出答案，不能防止检索系统返回数据。

### 4.4 索引更新与一致性

文档更新时，向量库需要支持：

- 新增：直接写入；
- 更新：先删旧向量再写新向量（或 upsert 覆盖）；
- 删除：按文档 ID 删除所有关联 chunk。

更新过程中要保证查询不读到「半更新」状态。常见做法是**双索引切换**：构建新索引 → 校验 → 原子切换查询流量 → 下线旧索引。

## 五、混合检索：BM25 + 向量

### 5.1 为什么纯向量不够

向量检索擅长语义匹配，但有三类盲区：

1. **精确标识符**：错误码、订单号、API 名称、版本号；
2. **低频专业术语**：语料中出现次数少，语义空间里没有足够信号；
3. **字面匹配**：用户直接引用文档原句。

BM25 是经典的关键词排序算法，它基于词频和逆文档频率，不关心语义，但对上述三类场景非常有效。

### 5.2 BM25 的价值

BM25 的公式可以简化理解为：

$$
\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})}
$$

其中 $f(t,d)$ 是词 $t$ 在文档 $d$ 中的频率，$\text{IDF}(t)$ 是逆文档频率，$k_1$ 控制词频饱和速度，$b$ 控制文档长度归一化强度。

工程上不需要手调 BM25，主流搜索引擎（Elasticsearch、OpenSearch）和向量库都内置了它。**它的价值在于提供一路「不依赖语义」的召回，和向量召回互补。**

### 5.3 融合排序：RRF 与加权

两路召回的结果需要融合。最简单有效的是 **RRF（Reciprocal Rank Fusion）**：

$$
\text{RRF}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}
$$

其中 $\text{rank}_i(d)$ 是文档 $d$ 在第 $i$ 路结果中的排名，$k$ 通常取 60。RRF 不需要归一化分数，只依赖排名，因此对两路分数量纲不敏感，非常稳健。

```python
def reciprocal_rank_fusion(result_lists, k=60):
    scores = {}
    for results in result_lists:
        for rank, doc in enumerate(results, start=1):
            scores[doc.id] = scores.get(doc.id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

另一种做法是加权分数融合（vector score × α + bm25 score × β），但需要归一化，调参更麻烦。**默认用 RRF，简单且效果稳定。**

### 5.4 融合比例与参数调优

混合检索的参数包括：两路各自的召回数量、融合公式、最终截断数量。这些参数都要在评测集上调：

- 向量召回数量（如 50）和 BM25 召回数量（如 50）决定了融合前的候选池；
- 融合后截断到 top-k（如 20）交给重排；
- 最终取 top-n（如 5）进入 prompt。

**每一层截断都是信息损失**。截断越早，成本越低，但召回风险越大。经验上，向量/BM25 各召回 50，融合后取 20 重排，最终取 5，是一个比较稳的起点。

## 六、重排序：精排决定上限

### 6.1 双塔 vs 交叉编码器

第一阶段检索（向量 + BM25）用的是**双塔（bi-encoder）**结构：查询和文档分别编码，点积比较。优点是快（文档向量可以离线算好），缺点是查询和文档没有交互，精度有限。

重排序用的是**交叉编码器（cross-encoder）**：把查询和文档拼在一起输入模型，输出相关性分数。模型可以在token级别比较查询和文档，精度显著更高，但每个候选都要跑一次模型，因此只能用于少量候选（通常 20～100 条）。

```text
双塔：query → [模型] → q_vec     doc → [模型] → d_vec     q_vec · d_vec
交叉：[query + doc] → [模型] → 相关性分数
```

### 6.2 重排的位置与成本

重排通常放在融合之后、组装 prompt 之前：

```text
向量 top-50 + BM25 top-50 → RRF 融合 → top-20 → 交叉编码器重排 → top-5 → prompt
```

重排模型的选择要以官方模型卡和自建评测为准，不要依赖第三方榜单。选型时关注：

- 模型支持的最大输入长度（查询 + 文档）；
- 是否支持中文；
- 推理延迟（每条候选多少毫秒）；
- 部署成本（自建 vs API）。

### 6.3 重排的失败模式

重排不是万能的，常见失败模式：

1. **位置偏差**：训练数据里靠前的文档更常被标注为相关，模型学到「靠前的就是好的」。
2. **长度偏差**：长文档更容易被判定为相关（包含更多关键词）。
3. **领域不匹配**：通用重排模型在专业领域（医疗、法律、工业）表现下降。
4. **过度截断**：候选池太小，重排再准也救不回漏掉的文档。

**重排是锦上添花，不是雪中送炭**：如果召回阶段漏掉了正确文档，重排无法凭空找回来。

## 七、检索评估：没有评估就没有优化

### 7.1 检索指标

假设评测集里有若干查询，每个查询标注了相关文档集合 $R(q)$。检索系统返回排序后的文档列表，常用指标：

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| Recall@K | $\frac{|R(q) \cap \text{top-}K|}{|R(q)|}$ | top-K 召回了多少比例的相关文档 |
| Precision@K | $\frac{|R(q) \cap \text{top-}K|}{K}$ | top-K 里有多少是相关的 |
| MRR | $\frac{1}{|Q|} \sum_q \frac{1}{\text{rank}_q}$ | 第一个相关结果的平均倒数排名 |
| NDCG@K | $\frac{\text{DCG}@K}{\text{IDCG}@K}$ | 考虑相关度分级和位置的排序质量 |

**RAG 场景优先看 Recall@K**：因为检索的目标是「不漏」，漏掉的文档在生成阶段无法弥补。K 的取值要和最终进入 prompt 的文档数对应，通常看 Recall@5 和 Recall@20。

### 7.2 生成端评估

检索对了不代表答案对。生成端常用三类指标：

- **忠实度（Faithfulness）**：答案是否只基于检索到的证据，没有编造。
- **相关性（Relevance）**：答案是否回答了用户问题。
- **引用正确性**：答案引用的来源是否真的支持对应结论。

忠实度通常用 LLM-as-Judge：把证据和答案一起给一个裁判模型，判断答案中的每个论断是否有证据支持。LLM-as-Judge 有偏差（偏好长答案、偏好特定风格），**只能作为回归测试的相对指标，不能作为绝对真值**。

### 7.3 构建评测集

评测集是 RAG 工程最值钱的资产，构建方法：

1. **真实问题**：从线上日志里抽样，脱敏后人工标注相关文档。
2. **合成问题**：用 LLM 基于文档生成问题，再人工筛选（快速但分布可能偏离真实）。
3. **边界样本**：故意构造容易出错的问题（同义词、多跳、否定、时效性）。

评测集规模不需要大：**50～200 条高质量样本足以支撑参数调优和版本回归**。每条样本至少包含：问题、相关文档 ID、可选的标准答案。

### 7.4 回归测试与 A/B

每次改动（换 embedding 模型、改 chunk 大小、调检索参数）都跑一次评测集，对比关键指标：

```text
改动前：Recall@5 = 0.82，MRR = 0.71，P95 延迟 = 380ms
改动后：Recall@5 = 0.85，MRR = 0.74，P95 延迟 = 410ms
```

如果只有主观感受没有数字，就无法判断改动是否值得。**任何没有评测集支撑的优化，都是赌博。**

线上还可以做 A/B：把一部分流量路由到新配置，对比用户反馈（点赞/点踩/追问率）。但 A/B 样本量小、周期长，**评测集才是日常迭代的主力**。

## 八、失败模式与排查

### 8.1 先定位：检索失败还是生成失败

RAG 出问题时，第一步不是调 prompt，而是**把检索和生成分开定位**：

```text
1. 把检索到的证据打印出来
2. 问：这些证据里有没有能回答问题的内容？
   - 没有 → 检索失败（切分/embedding/检索/重排问题）
   - 有 → 生成失败（prompt/模型/上下文长度问题）
```

这一步能省掉大量无效排查。**大多数 RAG 问题其实是检索问题，而不是模型问题。**

### 8.2 常见失败模式

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 答案正确但没引用来源 | 引用逻辑缺失 | 检查后处理与引用模板 |
| 答案包含文档里没有的信息 | 模型幻觉 | 加强 prompt 约束 + 忠实度评测 |
| 召回内容不相关 | embedding 不匹配 / chunk 过大 | 换模型、调粒度、看 Recall@K |
| 专有名词搜不到 | 向量盲区 | 加 BM25、同义词词典 |
| 多跳问题答错 | 单次检索信息不足 | 查询分解、多轮检索 |
| 文档更新了答案没变 | 索引未更新 | 检查增量更新与删除逻辑 |
| 不同租户数据串了 | 权限过滤缺失 | 检索层加租户过滤 |

### 8.3 可观测性

线上 RAG 至少要记录：

- 查询文本、改写后的查询；
- 每一路召回的文档 ID 与分数；
- 重排后的顺序与分数；
- 最终进入 prompt 的文档 ID；
- 生成的答案与引用；
- 各阶段耗时。

这些日志是排查和评测集建设的原料。**没有 trace 的 RAG 系统，出问题只能靠猜。**

### 8.4 调试流程

推荐的排查顺序：

```text
现象 → 取一个具体失败 case → 打印检索证据 → 判断检索/生成
→ 如果检索失败：看召回列表里有没有正确文档
   → 没有：查切分、embedding、BM25、融合参数
   → 有但排名靠后：查重排
→ 如果生成失败：查 prompt、上下文长度、模型版本
→ 修复后用评测集回归
```

## 九、进阶：Graph RAG、Agentic RAG 与多跳检索

### 9.1 Graph RAG

传统 RAG 以文本块为检索单位，适合局部事实问答；但面对「某系统的整体架构演进」「这些概念之间的关系」这类全局性问题，切块会丢失全局结构。

Graph RAG 的思路是：把文档中的实体和关系抽成图，检索时既查文本块也查图路径，必要时用社区摘要（community summary）回答全局问题。代价是需要实体抽取、图构建和维护成本，**适合文档量大、关系密集、全局问题多的场景**。

### 9.2 Agentic RAG

把 RAG 放进 Agent 循环，让模型自己决定：

- 是否需要检索；
- 用什么查询检索；
- 检索结果不够时如何改写查询再检索；
- 是否需要调用其他工具（数据库、API）。

Agentic RAG 更灵活，但引入了不确定性：步数变多、延迟变大、失败路径变复杂。**简单问答不需要 Agent，复杂多步任务才值得。**

### 9.3 多跳检索与分解

「A 公司的创始人在 B 公司担任什么职位」这类问题需要两次检索：先查 A 的创始人，再查该人在 B 的职位。处理方式：

- **查询分解**：把复杂问题拆成多个子问题，分别检索后合并。
- **迭代检索**：根据第一轮结果生成第二轮查询。
- **图检索**：在知识图谱上做多跳遍历。

多跳是 RAG 的难点，也是评测集里最该覆盖的样本类型。

### 9.4 何时不该用 RAG

RAG 不是万能的。如果文档总量不大（比如几十万字以内），且上下文窗口足够，**直接把文档放进 prompt 可能比 RAG 更简单、更准**。RAG 的代价是管道复杂度，只有当文档量大到无法一次塞进上下文，或者需要跨大量文档检索时，才值得引入。

## 十、生产化清单

### 10.1 数据更新与一致性

- 文档更新后，索引更新延迟是多少？能否接受？
- 删除文档时，向量、BM25、缓存是否同步清理？
- 索引重建期间，查询是否可用？是否需要双索引切换？

### 10.2 权限与多租户

- 检索层是否强制过滤租户/部门/角色？
- 生成层是否还有二次权限校验？
- 日志里是否记录了越权尝试？

**权限过滤必须在检索层**，不能依赖模型「不要回答」。

### 10.3 成本与延迟

| 组件 | 成本项 | 优化方向 |
| --- | --- | --- |
| Embedding | 按 token 计费 | 批量、缓存、增量 |
| 向量库 | 存储 + 查询 | 量化、分片、索引参数 |
| 重排 | 按候选数计费 | 控制候选数、蒸馏小模型 |
| 生成 | 按 token 计费 | 控制上下文长度、缓存前缀 |

### 10.4 监控指标

线上至少监控：

- 检索指标：Recall@K（离线评测）、召回为空率、平均召回分数；
- 生成指标：忠实度、用户反馈（点赞/点踩）；
- 性能指标：P50/P95 延迟、各阶段耗时；
- 稳定性：索引更新失败率、查询超时率、权限拦截次数；
- 成本：单次查询 token 数、日调用量。

## 十一、小结

把整篇文章压缩成六句话：

1. RAG 的上限由检索决定，下限由生成决定；优化重点是检索管道。
2. 切分要按语义单元，粒度用评测集调，不要照抄参数。
3. Embedding 模型没有最好，只有最适合你的语料，必须自建评测。
4. 纯向量有盲区，BM25 + RRF + 重排是稳定组合。
5. 没有评测集，所有优化都是赌博；先建 50～200 条评测集再迭代。
6. 权限过滤放检索层，trace 和监控是生产化的底线。

RAG 不难，但琐碎。真正的工程能力不是把 demo 跑通，而是把每一个「大概」变成「可测量、可回归、可维护」。
