## 引言：把「用哪个模型」当成一个可测量的工程决策

默认所有请求都发给最强的大模型，是成本失控最常见、也最容易掩盖的起点。

很多团队的线上链路长这样：用户发来一条请求，网关把它原样交给一个昂贵的大模型，拿到回答就返回，日志里只记了 token 数和总耗时。三个后果随之而来：简单问题（查格式、改写、抽取字段）也在烧大模型的额度；延迟被大模型的长尾拖住；一旦模型供应商涨价或限流，整条链路没有退路。

「大小模型分工」不是把便宜模型随便塞进去省钱，而是一个带约束的决策问题：在给定质量下限和可接受延迟的前提下，让尽可能多的请求由小模型完成，同时保证小模型确实答得对。这件事拆开，是四个可工程化的子问题：

- **能力问题**：小模型怎么才能接住那些请求？靠蒸馏、量化，或者干脆换一个更合适的模型尺寸。
- **分解问题**：一个复杂请求能不能拆成几段，让不同模型各做擅长的一段？级联（cascade）就是把「先小后大」做成流水线。
- **决策问题**：路由器（router）怎么知道这条请求该给谁？它需要特征、训练数据和线上置信度。
- **兜底问题**：路由错了怎么办？错误率怎么度量、怎么回退、怎么在不降级质量的前提下控住成本。

这篇文章按这个顺序展开，最后给一份落地清单。全文区分三类陈述：**已确认**（有论文或官方文档支撑的数字）、**工程经验**（常见做法，数字随场景变化）、**待验证**（需要你在自己的流量上测）。

## 一、三角不可能：成本、延迟、质量

先定义三个维度，再谈取舍。脱离度量口径谈「大模型更好」没有意义。

### 1.1 三个维度的定义

| 维度 | 常用度量 | 说明 |
| --- | --- | --- |
| 成本 | 每百万 token 输入/输出单价、单次请求成本、单位时间 GPU 成本 | 输入和输出分开计价，输出通常更贵 |
| 延迟 | TTFT（首 token 延迟）、TPOT（每输出 token 延迟）、端到端 p50/p95/p99 | 交互式产品看 p95，批处理看吞吐 |
| 质量 | 任务级正确率、相对强模型的保持率（performance retention） | 「保持率」比绝对分更有用，见 1.3 |

延迟结构值得单独说一句：生成式模型是「预填充 + 解码」两段，预填充计算受限（compute-bound），解码带宽受限（memory-bound）。因此首 token 延迟主要取决于输入长度和算力，而总延迟主要取决于输出长度和显存带宽。同一模型、同一输入，输出越长越慢，这也是路由系统必须按「输出长度」而不是「输入长度」估成本的原因。

### 1.2 大小模型的真实价格结构

价格是供应商定的，我们只引用论文里已核实的结构性事实，不引用具体厂商的当前报价。

**已确认**：FrugalGPT 论文（arXiv:2305.05176）指出，不同 LLM API 之间的定价可以相差两个数量级，这正是「路由有收益空间」的根本原因——如果所有模型同价，路由就只剩延迟收益。同一篇论文还指出，模型的能力与价格并不同步：更贵的模型不一定在所有任务上更好，这为「按任务难度分配模型」提供了依据。

**工程经验**：把成本拆成三块——输入 token 成本、输出 token 成本、以及被重复计费的上下文成本。很多链路的成本失控来自上下文：每次请求都带完整的系统提示、历史对话、检索片段，简单任务也在为长上下文付费。

| 成本来源 | 大模型 | 小模型 | 路由能改变什么 |
| --- | --- | --- | --- |
| 输入单价 | 高 | 低 | 选小模型即省 |
| 输出单价 | 高 | 低 | 简单任务输出短，省得更多 |
| 上下文重复 | 每次都带全量 | 同样问题 | 与路由无关，需单独治理 |
| 冷启动/常驻开销 | 高 | 低 | 小模型可常驻，大模型按需 |
| 失败重试成本 | 高 | 低 | 小模型先试，失败再升级 |

### 1.3 质量的正确度量：保持率而非绝对分

路由系统的目标不是「每个任务都满分」，而是「在质量下限之上，成本最低」。因此最有用的质量指标是**保持率**：

```text
保持率 = 路由系统的任务得分 / 始终使用最强模型的同一任务得分
```

RouteLLM 的论文（arXiv:2406.18665）用的就是「达到 GPT-4 性能的 95%」这种表述，并报告了为达到该目标所需的大模型调用比例。这个口径比「准确率提升 x%」更可落地，因为它把成本和质量绑在同一个坐标里。

这也解释了为什么评测章节要画「成本-质量曲线」而不是单个点：一个路由系统的价值，是它能把曲线往左上角推多少。

## 二、蒸馏：让小模型继承大模型的能力

蒸馏（knowledge distillation）是把一个大模型（教师）的能力迁移到一个小模型（学生）的技术族。它的核心思想由 Hinton、Vinyals 与 Dean 在《Distilling the Knowledge in a Neural Network》（arXiv:1503.02531）中提出：不要只用硬标签训练学生，还要让学生拟合教师的软标签（soft targets），因为软标签携带了类别之间的相似性信息。

蒸馏有三条主要路线，区别在于「教师的知识从哪一层取」。

### 2.1 三条蒸馏路线

| 路线 | 教师提供什么 | 学生拟合什么 | 代表工作 |
| --- | --- | --- | --- |
| logits 蒸馏 | 输出层概率分布 | 软标签 + 硬标签 | Hinton et al. 2015（arXiv:1503.02531） |
| 特征蒸馏 | 中间层激活 | 中间层表征 | FitNets（arXiv:1412.6550）、DistilBERT（arXiv:1910.01108） |
| 数据合成蒸馏 | 生成的样本/轨迹 | 输入-输出对 | Self-Instruct（arXiv:2212.10560）、Orca 2（arXiv:2311.11045） |

三条路线不互斥。现代小模型往往同时用 logits 蒸馏和特征蒸馏；数据合成则常作为「造训练集」的前置步骤。

### 2.2 logits 蒸馏：软标签与温度

教师对某个输入给出概率分布，而不是只给一个正确答案。学生用带温度参数 $T$ 的 softmax 去拟合这个分布：

$$p_i^{(T)} = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

$T$ 越大，分布越平滑，暴露的「暗知识」（dark knowledge）越多；$T=1$ 时就是普通 softmax。训练损失是教师分布与学生分布的交叉熵，再叠加一个对硬标签的交叉熵：

```python
import numpy as np


def softmax(logits, temperature=1.0):
    """带温度的 softmax，数值稳定版本。"""
    z = np.asarray(logits, dtype=np.float64) / temperature
    z = z - z.max(axis=-1, keepdims=True)
    exp = np.exp(z)
    return exp / exp.sum(axis=-1, keepdims=True)


def distillation_loss(student_logits, teacher_logits, hard_label,
                      temperature=2.0, alpha=0.5):
    """logits 蒸馏损失：软标签 KL + 硬标签交叉熵。

    alpha 越大越偏向教师的软标签，越小越偏向真实标签。
    """
    t = float(temperature)
    p_teacher = softmax(teacher_logits, t)
    p_student = softmax(student_logits, t)
    # 软标签项：KL(teacher || student)，缩放 T^2 保持梯度量级
    eps = 1e-12
    soft = -(p_teacher * np.log(p_student + eps)).sum(axis=-1).mean()
    soft = soft * (t * t)
    # 硬标签项：普通交叉熵
    log_p = np.log(softmax(student_logits, 1.0) + eps)
    hard = -log_p[:, int(hard_label)].mean()
    return float(alpha * soft + (1.0 - alpha) * hard)
```

注意 `np.log` 前的 `eps`：真实实现里教师分布可能有零概率项，直接取对数会得到 `-inf`。生产代码还应当处理教师和学生的词表大小不一致（需对齐到子词表）。

### 2.3 特征蒸馏：FitNets 与中间层对齐

logits 蒸馏只看输出，信息经输出层压缩后损失很大。特征蒸馏让学生去拟合教师的中间层激活。FitNets（arXiv:1412.6550）是这条路线的起点，它用教师的中间层作为 hint，训练更薄更深的网络。

DistilBERT（arXiv:1910.01108）把特征蒸馏用到 Transformer 上，采用三重损失：语言模型损失 + 蒸馏损失 + 余弦嵌入损失（对齐隐藏状态的方向）。其结论是：预训练阶段就蒸馏，可以让学生体积减少 40%、保留 97% 的语言理解能力、推理快 60%。

| 模型 | 蒸馏阶段 | 教师 | 规模变化 | 质量 | 速度 |
| --- | --- | --- | --- | --- | --- |
| DistilBERT（arXiv:1910.01108） | 预训练期 | BERT | 体积 -40% | 保留 97% 语言理解 | 快 60% |
| TinyBERT（arXiv:1909.10351） | 预训练 + 任务特定 | BERT_BASE | 小 7.5× | GLUE 达 BERT_BASE >96.8% | 快 9.4× |

TinyBERT 的两阶段设计值得借鉴：先做通用预训练蒸馏，再在具体任务上做任务特定蒸馏。后者对下游质量的提升通常比只蒸馏一次更明显，**工程经验**是：如果只蒸馏一次，优先蒸馏到「接近上线任务」的那一层。

### 2.4 数据合成蒸馏：Self-Instruct、Orca 2 与 GKD

第三条路线不迁移参数，而是迁移「数据」。让教师批量生成输入-输出对，再用这些数据训练学生。

- **Self-Instruct**（arXiv:2212.10560）：用语言模型自己生成指令、输入和输出，再用这些样本微调原模型。论文报告在 Super-NaturalInstructions 上比原模型绝对提升 33%。它的价值在于把「造数据」自动化。
- **Orca 2**（arXiv:2311.11045）：不只给答案，还教小模型用不同的解题策略，包括逐步推理（step-by-step）、先回忆再生成（recall-then-generate）、回忆-推理-生成（recall-reason-generate）和直接作答。论文在 15 个 benchmark、约 100 个任务、超过 36,000 条 prompt 上训练，得到的小模型性能接近或超过 5–10 倍大的模型。这条路线的关键洞察是：**解释性轨迹比答案本身更有信息量**。
- **GKD**（arXiv:2306.13649）：on-policy 蒸馏。传统蒸馏用教师生成的序列训练学生，学生推理时面对的是自己生成的序列，存在训练/推理分布错配；GKD 改为让学生自生成序列、教师在这些序列上给反馈。这是「数据合成蒸馏」里解决分布错配的代表。

| 方法 | 教师提供 | 主要收益 | 代价 |
| --- | --- | --- | --- |
| Self-Instruct | 指令+输入+输出 | 造数据自动化 | 需要过滤低质量样本 |
| Orca 2 | 解释轨迹 | 小模型学会「怎么想」 | 轨迹生成成本高 |
| GKD | 学生自生成序列上的反馈 | 消除训练/推理错配 | 需要教师在线参与，推理成本高 |

### 2.5 蒸馏不是万能的：能力天花板

蒸馏的上限是学生架构的容量，不是教师的能力。**工程经验**里有三条硬约束：

1. 学生太小时，蒸馏只能逼近、不能超越。教师能力再强，学生也学不会它没有的归纳偏置。
2. 蒸馏对「事实性知识」效果差，对「模式/风格/推理模板」效果好。因此知识密集型任务不要指望蒸馏解决。
3. 蒸馏后的模型仍需量化与路由配合，单靠蒸馏通常不足以同时满足成本、延迟、质量。

这也解释了为什么后面要单独讲量化和路由：蒸馏管能力，量化管成本，路由管分配。

## 三、量化：在显存与精度之间换空间

量化把模型权重和激活从高精度（FP16/BF16）降到低位宽（INT8/INT4），直接减少显存和带宽需求。它与蒸馏正交：蒸馏改变能力，量化改变成本。

### 3.1 三类量化

| 类型 | 训练方式 | 校准数据 | 典型收益 | 适用场景 |
| --- | --- | --- | --- | --- |
| QAT（量化感知训练） | 训练中模拟量化 | 全量训练集 | 精度最高 | 从头训练或大改模型 |
| PTQ（训练后量化） | 不训练，只校准 | 少量校准样本 | 成本低、速度快 | 已有模型上线压缩 |
| 混合精度分解 | 分块处理离群值 | 不需要 | 高精度、低显存 | 大模型推理 |

线上落地绝大多数用 PTQ，因为它不需要重新训练。**工程经验**：PTQ 的质量高度依赖校准集，校准集应当来自真实流量分布，而不是随机文本。

### 3.2 主流量化方法

| 方法 | arXiv | 核心机制 | 报告结论 |
| --- | --- | --- | --- |
| LLM.int8() | 2208.07339 | 向量量化 + 混合精度分解 | 175B 模型显存减半，无性能退化 |
| GPTQ | 2210.17323 | 基于二阶信息的 one-shot 权重量化 | 175B 约 4 GPU 小时量化到 3/4 bit，A100 端到端约 3.25× 加速 |
| SmoothQuant | 2211.10438 | 把激活离群难度迁移到权重，W8A8 | 最高 1.56× 加速、2× 显存下降，530B 单节点服务 |
| AWQ | 2306.00978 | 激活感知，保护 1% 显著权重 | TinyChat 比 HF FP16 实现快 >3×，可把 70B Llama-2 放到移动端 GPU |

四条方法解决的是同一个问题的不同侧面：

- LLM.int8() 的观点是「离群值只占极少数」，把离群通道单独用高精度处理，其余走 INT8。论文称超过 99.9% 的数值走 8-bit 路径。
- GPTQ 的观点是「逐层重建」，用少量校准数据逐层量化并补偿量化误差。
- SmoothQuant 的观点是「激活难量化、权重好量化」，因此离线把激活的缩放难度等价迁移到权重上，实现全 INT8 矩阵乘。
- AWQ 的观点是「不是所有权重都重要」，保护约 1% 的显著权重通道即可大幅降低量化误差，并用等比缩放实现，避免混合精度带来的硬件低效。

### 3.3 位数、显存与实测预期

权重显存的理论下限很好算：参数量 × 每参数字节数。但实际部署还包含激活、KV 缓存和框架开销，所以实际占用通常高于理论值。

| 精度 | 每参数字节 | 7B 模型权重理论显存 | 说明 |
| --- | --- | --- | --- |
| FP16/BF16 | 2 | 约 14 GB | 基线 |
| INT8 | 1 | 约 7 GB | 需配合激活量化才有速度收益 |
| INT4 | 0.5 | 约 3.5 GB | 分组量化常用，需校准 |

**已确认**的参照点：GPTQ 论文报告 175B 模型可量化到 3 或 4 bit 且精度损失可忽略；AWQ 论文报告其 TinyChat 框架在桌面和移动 GPU 上都比 Hugging Face FP16 实现快 3 倍以上。

一个反直觉但重要的结论：**权重量化降显存明显，但不一定降延迟**。解码阶段是带宽受限，权重从 FP16 到 INT4 直接减少读取量，因此延迟通常受益；而如果激活没量化，矩阵乘仍走高精度，速度收益会打折。SmoothQuant 的价值正在于把激活也降到 8-bit。

```python
import numpy as np


def quantize_weight_block(weight, bits=4, group_size=128):
    """对称分组量化的最小实现（PTQ 校准阶段可用）。

    每个分组独立求缩放因子，避免全局离群值拉大整体误差。
    """
    w = np.asarray(weight, dtype=np.float32)
    rows, cols = w.shape
    assert cols % group_size == 0, "列数必须能被 group_size 整除"
    qmin, qmax = -(2 ** (bits - 1)), 2 ** (bits - 1) - 1
    out = np.zeros_like(w)
    scale = np.zeros((rows, cols // group_size), dtype=np.float32)
    for g in range(cols // group_size):
        block = w[:, g * group_size:(g + 1) * group_size]
        amax = np.abs(block).max(axis=1, keepdims=True)
        s = np.maximum(amax / qmax, 1e-8)
        scale[:, g] = s[:, 0]
        q = np.clip(np.round(block / s), qmin, qmax)
        out[:, g * group_size:(g + 1) * group_size] = q * s
    return out, scale
```

上面是伪代码级别的最小示意：真实量化还需要处理离群通道、KV 缓存量化、以及反量化与矩阵乘的融合。**工程经验**：先量化权重，再决定是否量化激活；如果发现延迟没降，优先检查是不是激活路径没有走低位宽。

## 四、任务分解与级联

「大小模型分工」有两种基本形态：**路由**是二选一（这条请求给谁），**级联**是先做一段再看要不要继续。级联天然更适合「难度未知、但可验证」的任务。

### 4.1 分解的四种模式

| 模式 | 分解依据 | 典型例子 | 对小模型友好度 |
| --- | --- | --- | --- |
| 按步骤分解 | 任务有明确阶段 | 先抽取字段，再生成文案，最后校对 | 高：每段都简单 |
| 按难度分解 | 同类型请求难度不同 | 简单改写走小模型，复杂推理走大模型 | 高：这正是路由 |
| 按知识域分解 | 需要特定知识 | 代码问题走代码模型，通用问题走通用模型 | 中：需先分类 |
| 按格式分解 | 输出结构可验证 | 先出结构化草稿，再渲染 | 高：结构可校验 |

前两种是路由，后两种更接近「先分类再分配」。实际系统常把两者叠起来：先按知识域分类，再在域内按难度路由。

### 4.2 级联：先小后大，按置信度升级

级联的核心是：**小模型先答，答得不确定就升级到大模型**。它比直接路由多了一步「用小模型的实际输出判断」，因此对小模型的系统性偏差更鲁棒。

```text
用户请求
    │
    ▼
[小模型] ── 高置信度 ──► 直接返回（成本 = 小模型成本）
    │
    └─ 低置信度 ──► [大模型] ──► 返回（成本 = 小 + 大）
```

级联的成本期望是：

$$C_{\text{cascade}} = C_{\text{small}} + p_{\text{upgrade}} \cdot C_{\text{large}}$$

其中 $p_{\text{upgrade}}$ 是升级概率。这个式子说明级联省钱的唯一来源是**让升级概率足够低**，而不是让大模型变快。这也意味着：级联的质量下限由大模型兜底，上限由小模型在简单请求上的正确率决定。

**已确认**的参照点：FrugalGPT 论文（arXiv:2305.05176）把 LLM 级联列为三类降本策略之一，并报告其级联方案最多可降本 98%，或在同等成本下比 GPT-4 准确率高 4%。

### 4.3 级联 vs 路由

| 维度 | 直接路由 | 级联 |
| --- | --- | --- |
| 决策依据 | 请求特征（可离线训练） | 小模型的实际输出置信度 |
| 额外推理开销 | 无 | 一次小模型推理 |
| 对小模型偏差的鲁棒性 | 较差 | 较好（用输出判断） |
| 延迟 | 最低（只调一次） | 差请求上更高（小 + 大） |
| 实现复杂度 | 低 | 中（需要置信度阈值） |
| 适用前提 | 有标注数据训练路由器 | 小模型能给出可解释的置信度 |

**已确认**的统一点：Dekoninck、Baader 与 Vechev 的《A Unified Approach to Routing and Cascading for LLMs》（arXiv:2410.10347）推导了最优级联策略并证明若干已有路由策略的最优性，把两者放进同一个 cascade routing 框架。论文的核心结论是：**真正关键的是一个好的质量估计器（quality estimator）**，路由和级联只是它的两种使用方式。

### 4.4 投机解码是级联的特例

投机解码（speculative decoding，arXiv:2211.17192；投机采样 arXiv:2302.01318）在结构上和级联同构：用一个小模型（draft model）快速生成候选 token，再用大模型并行验证，验证不通过就回退。区别是它发生在 token 级别、输出分布保持不变，因此是「无损」加速。

这个类比很有用：它说明「小模型起草、大模型验证」不是权宜之计，而是有理论保证的范式。本文不展开推理引擎细节（站内《大模型是怎么工作的：从 Token 到推理引擎的完整拆解》已有覆盖），只强调一点：**投机解码和任务级级联可以共存**，前者压单模型延迟，后者压整体成本。

```python
def cascade_route(request, small_model, large_model,
                  confidence_fn, threshold=0.85):
    """最小级联实现：小模型先答，低置信度升级到大模型。

    返回 (最终答案, 实际使用的模型名, 小模型置信度)。
    这是结构示意，confidence_fn 需要按业务实现。
    """
    answer_small, confidence = small_model.generate_with_confidence(request)
    if confidence >= threshold:
        return answer_small, "small", confidence
    answer_large = large_model.generate(request)
    return answer_large, "large", confidence
```

`confidence_fn` 的选择决定了级联的成败。常见做法有：取答案的序列概率、多次采样看一致性、让模型自评（如 AutoMix 的 few-shot 自验证，arXiv:2310.12963），或用规则校验结构化输出是否合法。**工程经验**：结构化输出场景优先用规则校验，比概率置信度稳定得多。

## 五、模型路由器的训练

路由器是「用请求特征预测该给哪个模型」的分类器。它不是玄学，而是一个有明确目标函数的监督/半监督问题。

### 5.1 路由问题的形式化

设请求为 $x$，可选模型集合为 $\{m_1, m_2, \dots, m_k\}$，模型 $m_j$ 在 $x$ 上的质量为 $q_j(x)$，成本为 $c_j$。路由目标是：

$$\text{选择 } m_j \text{ 使得 } q_j(x) \ge q_{\min}, \quad \text{且 } c_j \text{ 最小}$$

如果质量不可直接观测，就用代理目标：预测「小模型是否能达到质量下限」。于是路由变成一个二分类问题：`small_ok(x) ∈ {0, 1}`，标签来自离线评测（用强模型当标注器，或人工标注）。

**已确认**的参照点：Hybrid LLM（arXiv:2404.14618）按预测的 query 难度和期望质量路由，报告最多可减少 40% 的大模型调用而质量不降。RouteLLM（arXiv:2406.18665）则用偏好数据训练路由器，报告在保持 GPT-4 95% 性能的同时，MT Bench 降本超过 85%。

### 5.2 四类路由器

| 路由器类型 | 决策方式 | 训练数据 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| 规则/启发式 | 关键词、长度、语言、结构化程度 | 无 | 零成本、可解释 | 上限低、维护麻烦 |
| 相似度加权排序 | 找最相似的历史请求，按表现投票 | 历史请求+结果 | 无需训练大模型 | 依赖特征表示 |
| 矩阵分解 | 请求-模型偏好矩阵分解 | 偏好数据 | 便宜、可迁移 | 冷启动差 |
| 学习型分类器 | BERT/LLM 分类器 | 标注数据 | 上限高 | 需要标注、需要迭代 |

RouteLLM 比较了这四类（其论文中还包括 causal LLM classifier），结论是：矩阵分解路由器用 26% 的 GPT-4 调用即达到 95% 的 GPT-4 性能，加入 judge 增强后降到 14%；在 MMLU 上，用约 1500 条 golden-label 样本（不到 2% 训练数据）增强后，最佳 causal LLM 路由器用 54% 的 GPT-4 调用达到 95% 性能。这些数字说明：**训练数据的「质」比「量」更关键**。

### 5.3 训练数据从哪来

| 数据来源 | 获取方式 | 偏差风险 |
| --- | --- | --- |
| 线上真实流量 + 事后标注 | 采样请求，用强模型或人工判对错 | 低，但标注贵 |
| 偏好数据（如 Chatbot Arena） | 复用公开对战数据 | 中，分布与你的业务可能不同 |
| 合成数据（Self-Instruct 式） | 大模型批量生成请求和答案 | 高，容易与真实分布错配 |
| 公开 benchmark | 直接用 MMLU/GSM8K 等 | 高，榜单分布不等于业务分布 |

**工程经验**：不要只用公开 benchmark 训练路由器。正确做法是取一小批真实流量（哪怕只有几百条），用强模型标注后训练，再上线后用新流量持续校准。RouteLLM 在 MMLU 上仅用约 1500 条 golden-label 样本就显著提升，说明**少量高质量真实标注**胜过大量合成数据。

### 5.4 路由特征工程

路由器的上限由特征决定。以下特征在多个系统中被验证有效，按获取成本从低到高排列：

| 特征 | 获取成本 | 预测什么 |
| --- | --- | --- |
| 输入长度、输出长度预估 | 极低 | 成本与延迟 |
| 语言、是否代码、是否含表格 | 低 | 知识域 |
| 是否命中结构化 schema | 低 | 可规则校验程度 |
| 历史同用户请求的成功率 | 中 | 用户专属难度 |
| 小模型置信度 | 中（需先跑小模型） | 是否需要升级 |
| 检索到的上下文密度 | 中 | 任务复杂度 |
| 强模型对该请求的历史表现 | 高 | 任务难度 |

最后两类特征指向同一个结论：**路由与级联并非互斥，最好的系统往往把小模型置信度作为路由特征之一**。这与 4.3 节「质量估计器是关键」的结论一致。

```python
from dataclasses import dataclass


@dataclass
class RouteDecision:
    model: str
    reason: str
    estimated_cost: float


def route_request(request_text, small_confidence, features,
                  threshold=0.85, small_cost=1.0, large_cost=20.0):
    """规则 + 置信度混合路由器（可解释基线）。

    features 至少包含: length_bucket, has_code, schema_ok
    """
    # 强规则：结构化输出合法且短请求，直接走小模型
    if features["schema_ok"] and features["length_bucket"] == "short":
        return RouteDecision("small", "schema_short", small_cost)
    # 置信度：小模型有把握就不升级
    if small_confidence is not None and small_confidence >= threshold:
        return RouteDecision("small", "confident", small_cost)
    # 代码类请求通常需要更强模型
    if features["has_code"]:
        return RouteDecision("large", "code_task", large_cost)
    return RouteDecision("large", "default", large_cost)
```

上面是有意写得「笨」的基线：它的价值不在准确率，而在**可解释、可回归测试**。真实系统会把 `route_request` 换成训练好的分类器，但保留同样的接口和同样的兜底路径。

矩阵分解路由器的训练思路（伪代码）：

```text
输入: 请求-模型偏好矩阵 R（行=请求，列=模型，值=该模型是否更优）
1. 对 R 做低秩分解，得到请求向量 U 和模型向量 V
2. 对新请求 x，用其历史相似请求的 U 行加权得到 u_x
3. 计算 u_x 与每个 V 行的内积，取成本最低且得分达标的模型
4. 线上持续用新偏好更新 R 的增量
```

**待验证**：矩阵分解的隐维度、更新频率对你的业务是否合适，需要在自己数据上扫参。RouteLLM 论文没有给出通用的超参数推荐值，只报告了其设置下的结果。

## 六、线上决策：错误率、回退与护栏

路由系统最大的风险不是「不够省」，而是「省错了」——把本该给大模型的请求给了小模型，用户拿到一个看似流畅但错误的答案。

### 6.1 路由错误的两种类型

| 错误类型 | 定义 | 用户感知 | 检测难度 |
| --- | --- | --- | --- |
| 漏升级（under-routing） | 该给大模型却给了小模型 | 答案错误或不完整 | 高，容易漏 |
| 过度升级（over-routing） | 该给小模型却给了大模型 | 无感知，只是变贵 | 低，看成本即可 |

两类错误的代价不对称：**漏升级伤质量，过度升级伤成本**。因此路由阈值通常应当偏向「宁可多升级」，再逐步收紧。

**已确认**的参照点：Dekoninck 等人的统一框架（arXiv:2410.10347）把最优策略表达为质量估计器的函数，说明「漏升级 vs 过度升级」的权衡不是拍脑袋定阈值，而是可以从质量估计器的误差分布推导。

### 6.2 回退与升级策略

| 策略 | 触发条件 | 代价 | 适用 |
| --- | --- | --- | --- |
| 阈值升级 | 小模型置信度 < 阈值 | 一次大模型调用 | 置信度可靠时 |
| 规则校验失败升级 | 结构化输出不合法 | 一次大模型调用 | 有 schema 的任务 |
| 用户显式升级 | 用户点「重新回答/换个模型」 | 一次大模型调用 | 交互产品 |
| 异步补偿 | 后台用大模型重跑并替换 | 双倍成本 | 高价值、低时效任务 |
| 全量回退 | 供应商故障 | 成本不可控 | 熔断场景 |

回退设计里最容易被忽略的是**延迟叠加**：级联在差请求上会同时付出小模型和大模型的延迟。交互式产品需要给升级路径设单独的延迟预算，必要时先返回小模型结果、再异步用大模型覆盖。

### 6.3 护栏指标

路由上线后，以下指标应当作为常设监控项：

| 指标 | 定义 | 建议告警方向 |
| --- | --- | --- |
| 小模型占比 | 走小模型的请求数 / 总请求数 | 突然下降可能是路由器漂移 |
| 升级率 | 触发升级的请求占比 | 突然上升需排查 |
| 升级后质量增益 | 升级请求上大模型 vs 小模型的质量差 | 增益低说明阈值过松 |
| 单位请求成本 | 总成本 / 请求数 | 与基线对比 |
| 漏升级率（抽样） | 抽样中「小模型错、大模型对」的比例 | 质量护栏核心 |
| 端到端 p95 延迟 | 含升级路径 | 与纯大模型基线对比 |

**工程经验**：把「漏升级率」做成抽样人工评测 + 强模型交叉评测的组合指标，比只看成本更能发现退化。这与站内《大模型评测体系：Benchmark 陷阱、LLM-as-Judge 与人工评测》的分层框架一致——路由评测属于 L2（Judge）与 L4（线上）的交叉地带。

```python
def evaluate_router(decisions, gold_labels, costs):
    """路由评测：分别统计漏升级、过度升级和单位成本。

    decisions: 路由器决策序列，元素为 "small"/"large"
    gold_labels: 每条请求是否小模型就够（1=够，0=不够）
    costs: 每次决策的实际成本
    """
    n = len(decisions)
    under = 0
    over = 0
    for d, g in zip(decisions, gold_labels):
        if d == "small" and g == 0:
            under += 1
        if d == "large" and g == 1:
            over += 1
    total_cost = sum(costs)
    return {
        "requests": n,
        "under_routing_rate": under / n if n else 0.0,
        "over_routing_rate": over / n if n else 0.0,
        "avg_cost": total_cost / n if n else 0.0,
        "large_share": sum(1 for d in decisions if d == "large") / n if n else 0.0,
    }
```

这个函数刻意只统计「路由决策」层面的错误，不统计模型本身的质量——后者属于模型评测，不属于路由评测。两者要分开看，否则路由阈值会被模型版本的升级牵着走。

## 七、评测：怎么衡量一个路由系统

路由系统的评测目标是回答两个问题：**质量保住了多少？成本降了多少？** 单看任何一个都会误导。

### 7.1 成本-质量曲线

把路由器的一个可调参数（如升级阈值）从松到紧扫描，横轴为单位请求成本，纵轴为质量保持率，得到一条曲线。

```text
质量保持率
 100% ┤                            纯大模型基线
      │                      ╭─────
      │                 ╭────
      │            ╭────
      │       ╭────
      │  ╭────
      │──
      └──────────────────────────────► 单位请求成本
        小模型基线
```

曲线越靠左上越好。**工程经验**：不要只测一个阈值就上线，至少测 3 个点，确认曲线形状符合预期——如果曲线很平，说明质量估计器不敏感，需要回头改特征。

### 7.2 路由错误率的分解

路由错误可以分解到三个来源，每个来源对应不同的修复手段：

| 错误来源 | 表现 | 修复方向 |
| --- | --- | --- |
| 质量估计器不准 | 置信度和真实正确率不相关 | 换特征、换估计器、加校准 |
| 训练数据偏差 | 某类请求系统性误判 | 补该类真实标注数据 |
| 分布漂移 | 上线后错误率随时间上升 | 定期重训、监控漂移 |

**已确认**的参照点：AutoMix（arXiv:2310.12963）专门处理「自验证有噪声」这个问题，用 POMDP 路由器而不是单次阈值决策，在 5 个模型、5 个数据集上把成本降低超过 50% 且性能可比。这印证了：**置信度有噪声时，需要把路由建模成序贯决策，而不是单次分类**。

### 7.3 评测指标表

| 指标 | 计算方式 | 用途 |
| --- | --- | --- |
| 质量保持率 | 路由系统得分 / 纯大模型得分 | 主指标 |
| 大模型调用占比 | 大模型调用数 / 总请求数 | 成本代理 |
| 成本节省率 | 1 - 路由成本 / 纯大模型成本 | 主指标 |
| 漏升级率 | 小模型错且大模型对的样本占比 | 质量护栏 |
| 过度升级率 | 小模型对但仍升级的比例 | 成本优化空间 |
| 每正确回答成本 | 总成本 / 正确回答数 | 综合效率 |

最后一行「每正确回答成本」是最接近业务价值的指标，但它需要质量标注。**工程经验**：在标注预算有限时，优先标注「路由器认为小模型能答对」的样本，因为那里才是漏升级的高发区。

## 八、落地清单

### 8.1 分阶段路线

| 阶段 | 目标 | 动作 | 验收标准 |
| --- | --- | --- | --- |
| 0. 度量基线 | 知道现在多贵多慢 | 记录每次调用的模型、输入输出 token、耗时、成本 | 有 p50/p95/p99 与单位成本 |
| 1. 任务分类 | 知道哪些请求简单 | 按知识域/格式/长度给请求打标签 | 能给出小模型占比上限的估计 |
| 2. 规则路由 | 快速验证收益 | 用规则把明确简单的请求导到小模型 | 小模型占比 > 0，质量不降 |
| 3. 置信度级联 | 处理难度未知 | 小模型先答 + 规则/置信度升级 | 漏升级率低于阈值 |
| 4. 学习型路由 | 提升上限 | 用真实标注训练分类器 | 同质量下成本低于规则路由 |
| 5. 持续校准 | 防漂移 | 定期抽样评测、重训、监控 | 指标稳定 |

### 8.2 上线检查清单

- [ ] 有纯大模型基线的质量与成本数据，可做对比。
- [ ] 路由决策可解释：每条请求能回答「为什么给这个模型」。
- [ ] 有明确的升级路径，且升级后的延迟在预算内。
- [ ] 漏升级率有抽样评测，而不是只看成本。
- [ ] 有熔断：供应商故障时能退回全量大模型或排队。
- [ ] 有灰度：路由策略按流量比例放量，可回滚。
- [ ] 日志记录路由原因，便于事后归因。
- [ ] 监控告警覆盖小模型占比、升级率、单位成本、p95 延迟。

### 8.3 常见反模式

| 反模式 | 后果 | 纠正 |
| --- | --- | --- |
| 只按输入长度路由 | 长而不难的请求被误判 | 加入任务类型与置信度 |
| 只看成本不看漏升级 | 质量悄悄劣化 | 把漏升级率纳入验收 |
| 用公开 benchmark 训路由器 | 与业务分布错配 | 用真实流量标注 |
| 阈值定死不再校准 | 分布漂移后失效 | 定期重训与监控 |
| 升级路径无延迟预算 | 交互式场景超时 | 单独设预算或异步补偿 |
| 小模型和大模型输出风格不一致 | 用户体验割裂 | 蒸馏风格或后处理对齐 |

## 小结

大小模型分工的本质，是把「用哪个模型」从默认行为变成可测量的决策：蒸馏和量化决定小模型的能力与成本边界，任务分解与级联决定请求的拆分方式，路由器决定单次请求的归属，而错误率与回退决定系统的可靠性下限。四个环节里，**质量估计器是贯穿始终的关键**——级联用它决定是否升级，路由用它决定是否分配给小模型，评测用它衡量系统是否退化。落地时不要一步到位：先建立度量基线，再用规则路由验证收益，然后引入置信度级联，最后才训练学习型路由器，并用持续的漏升级率监控守住质量下限。
